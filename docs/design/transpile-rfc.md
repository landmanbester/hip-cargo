## 1. Executive summary

This RFC proposes `hip-cargo transpile`: a command that compiles a deliberately restricted subset of stimela-style YAML recipes into an installable, Ray-orchestrated Python package. A recipe in the restricted subset becomes:

1. **Compilable** — it lowers to a concrete Python artifact (a runner module plus packaging metadata), not a structure interpreted at run time by a general framework; and
2. **Statically security-auditable** — the generated Python passes `ruff` and `bandit`, and the recipe grammar itself offers no surface to inject arbitrary code.

The transpiler emits a thin runner only. It does not re-implement a cab's core function. Every hip-cargo cab declares a plain, importable Python entry point (verified against the installed pfb-imaging cabs, which are all `flavour: python`, e.g. `command: pfb_imaging.core.init.init`; the `stokify` demonstrator below is built to the same contract). The runner imports that function and calls it. Each step is wrapped in a `@ray.remote` task carrying a per-step `runtime_env` — including the cab's already-declared container image and environment — and a per-step resource request (`num_cpus`/`num_gpus`/`memory`) on the decorator. Three consequences follow: the orchestrator need not install the wrapped package, because each step runs in its cab's container; the reproducibility unit is the container image, to the extent the cab pins an immutable tag or digest rather than a moving tag (the installed pfb cabs currently pin `:scatbeams`, which is mutable); and resources are declared per step rather than for the recipe as a whole. Steps are chained by passing Ray ObjectRefs between them: a step returns an `xr.Dataset`, the runner holds the ref Ray produces, and passes it to the next step. Two memory modes govern what crosses that boundary — `memory_greedy` returns a reified, plasma-resident dataset (disk fully bypassed between steps), while `memory_conservative` returns a small, lazily store-backed dataset (disk reads deferred to a shared store). Crucially, the driver only ever shuttles opaque refs; an intermediate dataset is deserialized only inside the containerized worker that consumes it, which is why the orchestrator — and the lightweight-installed package — never needs the heavy stack. Filesystem outputs remain available for steps that genuinely produce on-disk products.

One dependency in this design is worth surfacing immediately: it relies on Ray's per-task `runtime_env` `image_uri` to run each step in its cab's declared container. Upstream Ray marks `image_uri` as experimental, so this is a design dependency we must validate, not a finished mechanism.

Ray is central to the design: an earlier exploration considered dropping it and was rejected. Observability builds directly on the Ray Dashboard for cluster/task analytics, layered on hip-cargo's existing `apis`-branch monitoring stack (enumerated in Section 5). This RFC builds on substantial already-implemented infrastructure rather than starting green-field; the principal new work is the recipe → runner code generation and the per-step `runtime_env`/resource wiring.

The demonstrator is a new, purpose-built hip-cargo package — `stokify` — scaffolded via `hip-cargo init` to adhere strictly to the restricted subset. It exposes three steps: `init` (read a measurement set), `process` (transform coherencies into image-ready Stokes visibilities), and `image` (grid and image the Stokes visibilities), each returning an `xr.Dataset`. Building the demonstrator fresh, rather than transpiling an existing recipe, lets us exercise the in-memory ObjectRef model end-to-end without first refactoring a heavy downstream package, and it dogfoods the design philosophy the proposal advocates. It also keeps the pipeline within a single package and a single container image, where passing rich objects (`xr.Dataset`) between steps as ObjectRefs is deserialization-safe.

A few caveats are stated up front; none are blockers, and all are detailed in later sections.

- `memory_conservative` *defers* disk I/O to a shared store rather than eliminating it; only `memory_greedy` (plasma-resident) fully bypasses disk between steps. Conservative mode therefore assumes a store every worker can reach (shared mount or object store). Both modes still avoid *writing* intermediate products to disk, which is the shared win.
- In-memory ObjectRef outputs and per-step memory modes are new categories hip-cargo must grow to model — today it models only filesystem outputs (`@stimela_output`). This is the principal change to hip-cargo itself, detailed in §9.
- Transpiling an *existing* heavy package later (e.g. pfb-imaging) would additionally require a small Ray-ownership refactor in that package (~30–50 LOC, so its steps attach to the orchestrator's cluster instead of calling `ray.init()`/`ray.shutdown()` themselves). This is a future-integration cost, not a precondition for the `stokify` demonstrator, which is built to the contract from the start.
- Nested-resource budgeting on Ray remains a tuning concern for any step that spawns its own internal worker pools against the cluster.

This is not a replacement for stimela. It is an adjacent, narrower tool aimed at a subset of users for whom a smaller, stricter contract — auditable on shared HPC, compilable to a concrete artifact — is worth giving up stimela's universality.

## 2. Motivation

The audience for this proposal already runs stimela recipes daily on the SARAO compute environment. The motivation is therefore not "pipelines are useful" but a precise account of what a restricted, compiled tool buys a specific subset of users, and why that subset is real. Three threads run through this section: security on shared HPC, static analysability, and the wrapper standardization that hip-cargo already enforces, which is what makes a thin transpiler possible at all.

A framing note governs the whole section: stimela's universality is a reasonable design with real costs, not a flaw. A general workflow framework must accept arbitrary tools, arbitrary parameter-passing conventions, and arbitrary output formats, and stimela does this well; many SARAO colleagues depend on it precisely because of that generality. The argument below is that for a subset of recipes — those that can be expressed as declarative references between typed Python callables — a stricter contract is achievable and better on a few specific axes. Where stimela pays the cost of generality at run time, hip-cargo can decline to pay it because the cost was already paid once, by hand, at wrapping time.

The intended relationship is sequential, not competitive. stimela remains the de-facto general-purpose tool for *developing* pipelines: it is where a recipe is prototyped, explored, and iterated while its shape is still in flux. The proposal's claim is that once a recipe reaches a certain maturity — its steps stable, its tools known — maintainers should invest the one-time effort to wrap those tools into the (still-evolving) hip-cargo format and express the pipeline in the restricted subset. The payoff for that investment is the auditability, reproducibility, and in-memory orchestration described below. hip-cargo is therefore best understood as a *hardening* target for mature recipes, not a replacement for the development tool.

### 2.1 Security on shared HPC

A stimela cab may execute arbitrary shell commands, and recipes routinely do. The privilege model that is unremarkable on a single-user workstation becomes a real concern on a shared HPC cluster, where recipes run with the submitting user's full privileges. Because a cab may run arbitrary shell, reviewing a recipe before running it on a shared partition is equivalent to auditing arbitrary code, and there is no general, tractable way to certify by inspection that an arbitrary recipe is side-effect-free on shared infrastructure. This is an inherent property of any framework general enough to wrap arbitrary tools, stimela included; it is the cost of the generality, not a defect.

The restricted subset removes that surface by construction. It admits no shell steps and no arbitrary commands — only references to hip-cargo cabs, each of which resolves to an importable Python function. The recipe grammar has nowhere to put a shell string. The security boundary is the recipe grammar itself: there is no escape hatch to audit, because there is no escape hatch. (Because the artifact is then ordinary Python, it can also be handed to `ruff` and `bandit`; what those tools can and cannot certify is the subject of §2.2.)

### 2.2 Static analysability

The second cost of generality is that stimela's recipe content is, by design, not statically analysable. The formula DSL — `=GLOB(...)`, `=IF(...)`, `=IFSET(...)`, arithmetic, nested substitutions, `${self:...}` — is evaluated by stimela at run time against a runtime namespace. This is powerful and, for many recipes, necessary. It also means that what a parameter *is* cannot be known by reading the recipe; it can only be known by running the evaluator. `ruff` and `bandit` cannot reason about a value produced by a DSL they do not execute.

The restricted subset makes the opposite trade. Its only "computation" is plain namespace references (`=recipe.x`) and f-string-style interpolation (`{recipe.x}`). Everything else is typed value plumbing between cab references. The result is ordinary named-argument Python with no run-time-evaluated DSL: a binding in the recipe becomes a named argument in a generated call, so the data flow is visible on the page rather than hidden behind an evaluator. Two distinct things follow, and it is worth keeping them apart. First, the artifact is amenable to human review, because reading it does not require simulating a DSL. Second, it is amenable to `ruff` and `bandit`'s pattern checks — `bandit` in particular finds no dynamic `exec`/`eval`/shell-injection sinks, because the grammar admits none. A clean run is therefore a meaningful negative result given the input grammar, not a proof of behavioural safety and not a claim that these tools perform whole-program data-flow tracing; they do not.

The cost of this cut is stated plainly: the canonical SARA recipe in use today uses `=IF`, `=IFSET`, and arithmetic (e.g. `positivity: =IF(recipe.product == 'I', 1, 0)` and `nthreads: =recipe.nworkers * recipe.nthreads`). The demonstrator is therefore a deliberately flattened version of that recipe, with those expressions resolved by hand into concrete bindings. The proposal's claim is not that every existing recipe fits the subset; it is that a useful class of recipes can be *written to* fit it, and that those recipes gain auditability in return.

### 2.3 Wrapper standardization

This is the part of the proposal readers will find least familiar, and it is the argument the rest of the proposal rests on: it is the reason a *thin* transpiler is feasible rather than a re-implementation of stimela.

hip-cargo's existing discipline is that every external package is wrapped exactly once, in Python, by a maintainer who understands that package, into a fixed three-layer shape:

- `cli/` — a Typer CLI with `Annotated` types;
- `core/` — a plain Python implementation that absorbs the wrapped tool's quirks (its argument conventions, its output formats, its environment assumptions); and
- `cabs/` — an auto-generated stimela cab schema derived from the typed signature.

The consequence that matters here: from the outside, every hip-cargo-wrapped package looks identical — a typed Python function with a generated schema pointing at it. The idiosyncrasies that a general framework must accommodate at run time have already been normalised away, by hand, at wrapping time.

A transpiler consuming these cabs therefore does not need to implement stimela's universal-framework machinery. It needs no policy machinery, no parameter-passing flavours, no wrangler regexes for output parsing, and no formula DSL — because every cab it consumes is already a typed Python callable in a known shape. It also assumes a single cab flavour (`flavour: python`); this is not a property automatically guaranteed by wrapping but an enforced input restriction, the CASA/binary exclusion in Section 6. There is otherwise nothing left to interpret: the cab says `command: pfb_imaging.core.init.init`; the runner imports that and calls it with named arguments. That is the entire contract. Each item in this "need not implement" list maps onto a Section 6 exclusion — wrangler regexes onto "No wranglers", the formula DSL onto "No formula DSL", multiple flavours onto "No CASA/binary flavour" — so Section 6's cuts are the same facts viewed from the exclusion side.

The cost of each tool's idiosyncrasies is paid once, by the wrapper maintainer, rather than re-paid on every run by a framework that cannot assume the normalisation has happened. The transpiler benefits from standardization hip-cargo already enforces; it neither defines a new standard nor competes with stimela. Most of the apparent "missing features" in Section 6 are missing precisely because the wrapper already absorbed the need for them.

## 3. Design history and evolution

This proposal did not begin as a transpiler. It began as a *monitoring layer* for hip-cargo, and the path from there to here is worth recording — both because the lineage explains why the `apis` branch contains what it does, and because the monitoring work is not discarded by the pivot but inherited by it.

**The original intent — a monitoring dashboard.** The goal was to give any hip-cargo-scaffolded project an automatic, web-based dashboard for observing long-running scientific pipelines: check progress from a phone, watch convergence metrics tick over, inspect intermediate images, and control execution (kill a step, relaunch it with modified parameters). The reference use case was pfb-imaging's SARA deconvolution pipeline, and the design was driven directly by the `sara.yml` stimela recipe — the dashboard would parse that recipe, recover its DAG, and observe a `stimela run` of it.

**What was built.** The `apis` branch carries that substrate today, covered by 314 passing tests (§4 inventories it in full): a stdlib-only progress-event protocol with pipeline-level lifecycle events and an ergonomic `track_progress()` context manager; a Ray-based `ProgressAggregator` actor with ring-buffered event storage, metric history, and DAG-aware tracking; a FastAPI server with REST endpoints and push-based WebSocket streaming via a centralised `EventDispatcher`; a recipe parser that extracts DAG structure and parameter bindings; and a cab resolver that follows `_include` references to recover full parameter schemas from installed packages. One gap is worth stating here because it shapes the demonstrator: while this monitoring infrastructure exists *in hip-cargo itself*, `hip-cargo init` does **not** scaffold any of it into new projects. Enabling monitoring for a scaffolded project is currently a manual wiring step — adding the `hip-cargo[monitoring]` dependency, registering a `RayProgressBackend` via `set_backend(...)`, and instrumenting `core/` functions with `track_progress()`. The `stokify` demonstrator does that wiring by hand, which is both a necessary step for the spike and a concrete specification of what the §9.7 template changes should later automate.

**Why the design evolved.** Three realisations moved the design from "a dashboard that observes stimela pipelines" toward "a transpiler that compiles restricted recipes into Ray-orchestrated packages."

1. *The reference recipe was the wrong thing to observe.* `sara.yml` leans on exactly the stimela features that are opaque to static analysis — the formula DSL, alias broadcasts, conditional expressions (§2.2). A dashboard that *interprets* those at run time is useful, but it does nothing for the security concern (§2.1) that grows more acute as SARAO moves scientific workloads onto shared infrastructure. Observing an un-auditable pipeline more closely is not the same as making it auditable.

2. *The frontend was easier to derive than to discover.* An initial attempt to design the dashboard frontend in isolation (via Google Stitch) proved hard to get right. The lesson was architectural, not cosmetic: a dashboard that must *discover* a pipeline's structure at run time, by parsing recipes and polling APIs, is doing work a transpiler has already done at compile time. If the DAG, the per-step parameter schemas, and the resource shape are all known statically, the frontend can be *emitted from* that structure rather than reconstructing it live — simpler to build and more specific to the pipeline it serves (developed in §5.9).

3. *The monitoring substrate is exactly what a transpiled package needs.* The progress protocol, the Ray aggregator, and the FastAPI server are not stimela-specific; they are a general observability layer. Rather than build two systems — a monitoring dashboard for stimela now, a transpiler later — the monitoring work *becomes* the observability layer the transpiled package inherits. The roughly 70% of the system that already exists is reused, not thrown away; the transpiler is the remaining ~30% (§9).

**Why `stokify`, not `sara.yml`.** The canonical SARA recipe uses `=IF`, `=IFSET`, arithmetic, and alias broadcasts throughout — precisely the features the restricted subset excludes (§6). Beginning there would conflate two questions: "does the architecture work?" and "can we port an existing recipe?" The second is real and is addressed on its own terms (the conditional-by-specialization direction in §11; the pfb-imaging Ray-ownership refactor in §9), but it is not the right *first* question. `stokify` is therefore a new, purpose-built three-step package that adheres to the restricted subset from the start, letting the spike validate the target shape — ObjectRef chaining, per-step `runtime_env`, the driver-never-materializes principle, the monitoring integration — in isolation. The earlier locked direction for the spike was "generate the package now, run it later"; this RFC tightens that into a *runnable* demonstrator on **synthetic data** (no measurement-set or radio-astronomy dependencies), so reviewers can install it and watch real progress events stream, while live execution against a real measurement set and real per-step containers stays a separate opt-in milestone (§12).

**The monitoring vision, delivered differently.** Nothing about the original vision is abandoned — a DAG view, live per-step progress and metrics, and job control (kill/relaunch with edited parameters) remain the goal. What changes is the delivery mechanism: instead of a standalone dashboard that discovers pipeline structure at run time, the structure is known at compile time and baked into a pipeline-specific frontend the transpiler emits, with the existing monitoring *server* still handling the live, dynamic parts (§5.9). The demonstrator exercises this substrate end-to-end: `stokify`'s runner emits `PIPELINE_STARTED` / `STEP_STARTED` / `STEP_COMPLETED` / `COMPLETED` events through `track_progress()`, which flow through `RayProgressBackend` to the `ProgressAggregator` actor and on to the server's REST and WebSocket endpoints — the original vision's plumbing, now driven by a compiled pipeline rather than an interpreted recipe.

## 4. Current state of the `apis` branch

This RFC is a proposal to *complete* a partially built system, not to start one. The `apis` branch already carries the event-and-monitoring substrate, the recipe and cab introspection layer, and the shared codegen IR that the transpiler will reuse. The work below exists today and is covered by a passing test suite (314 tests collected on the branch, including end-to-end integration against a real local Ray cluster). What it lacks is the one piece this RFC is about: a path from a parsed recipe to an executable, Ray-orchestrated package. The inventory is grouped by concern so the reader can see how close to the surface the missing piece sits.

**Progress protocol.** `src/hip_cargo/utils/progress.py` defines `EventType` (a `StrEnum` whose 11 members include the four pipeline-level ones — `PIPELINE_STARTED`, `STEP_STARTED`, `STEP_COMPLETED`, `STEP_FAILED` — alongside the per-worker `STARTED`/`PROGRESS`/`LOG`/`ARTIFACT`/`METRIC`/`COMPLETED`/`FAILED`), a `ProgressBackend` `Protocol`, and a `NullBackend` default so the protocol is genuinely zero-overhead when no monitoring is attached. The module-level API is `set_backend` / `get_backend` / `emit`. `progress_context.py` adds the `track_progress()` context manager, which emits `STARTED` on entry, `COMPLETED` on clean exit and `FAILED` (carrying the exception string) on error, and groups events by a `pipeline_run_id`. The whole protocol depends on nothing beyond the standard library, which is what lets it sit inside the lightweight driver without dragging in Ray.

**Ray aggregation.** `src/hip_cargo/monitoring/ray_backend.py` provides `ProgressAggregator`, a named, `lifetime="detached"` Ray actor backed by a ring buffer that bounds memory by trimming the oldest events when full. Its methods (`push_event`, `get_latest`, cursor-based `get_events(job_id, since_index)`, `get_all_jobs`, `get_metrics_history`, `get_pipeline_dag`) are the read/write surface the server polls. `RayProgressBackend` pushes events fire-and-forget; `get_or_create_aggregator()` is the idempotent handle.

**FastAPI server + dispatcher.** `server.py` exposes four endpoint groups: job management proxied to the Ray Jobs Python SDK (`JobSubmissionClient`) under `/api/jobs...` plus `POST /api/pipelines/submit`; progress data over both REST (`/api/progress/{job_id}`, `.../events`, `.../metrics/{name}`, `.../dag`) and a WebSocket at `/ws/progress/{job_id}`, all served from the aggregator; recipe inspection (`/api/recipes`); and cab-schema introspection (`/api/commands`). `dispatcher.py` runs a single `EventDispatcher` poll loop that fans one event stream out to N WebSocket clients with periodic heartbeats and guaranteed connection cleanup. `config.py` is `MonitorSettings` (pydantic-settings, `HIPCARGO_` env prefix).

**Recipe parser.** `recipe_parser.py` turns a recipe YAML into a `RecipeDAG` of `RecipeInput`, `RecipeStep`, and `StepParam` objects, with each parameter classified as literal vs. binding (an `=`-prefixed stimela expression), `recipe.*` references regex-extracted from bindings, and **linear** edges. It is explicit, in both docstring and behaviour, that it does not *evaluate* stimela expressions — it records their text and their references.

**Cab resolver.** `cab_resolver.py` resolves a `(pkg.cabs)file.yml` include via `importlib` into a `CabSchema` that carries the `command` (the importable `module.func` — the python flavour this RFC depends on) and a typed list of `CabParam` (name, dtype, required, default, choices, policies, metadata). `recipe_discovery.py` locates recipe files within a project.

**Shared IR + codegen.** `src/hip_cargo/utils/spec.py` defines the neutral IR (`ParamSpec`, `CommandSpec`, `ModuleSpec`); `introspector.parse_module()` is the single CST walk feeding two consumers, `generate-cabs` and `generate-schemas`. `cab_to_function.generate_parameter_signature()` turns a parameter dict into an `Annotated` Typer option and `generate_function_body()` emits the lazy-import + typed-call + container-fallback body. `generate_schemas` renders, runs ruff, then byte-compares before writing so generation is idempotent. This is the machinery the transpiler will lean on rather than reinvent.

**Tests.** The suite exercises all of the above; the integration tests (`tests/test_integration.py`) stand up a real local Ray cluster and drive a full `PIPELINE_STARTED -> STEP_STARTED -> STEP_COMPLETED -> COMPLETED` lifecycle through the aggregator and server (the Ray Jobs client is faked; the aggregator/actor path is real).

### Limitations

The honest gaps are concentrated and known. The DAG edges are **linear-only** — they are built from declaration order, not from data-flow analysis of the `recipe.*` references, so the parser will not yet recover a true dependency graph. `POST /api/pipelines/submit` constructs a fragile `stimela run <recipe> <key> <param_args>` command string; this is a placeholder the RFC proposes to replace with direct invocation of the transpiled runner. The WebSocket aggregator only replays from the subscriber's join-time cursor forward, so a late subscriber does not see history. The recipe parser does **not** evaluate or translate expressions, does not resolve aliases, and skips the `opts` block entirely (`_SKIP_KEYS = {"_include", "opts"}`) — consistent with the deliberate grammar cuts in section 6, but it means the current parser is an inspector, not a compiler front end. Most importantly, **no pipeline runner exists yet**: everything above observes and describes pipelines, but nothing here turns a `RecipeDAG` plus resolved `CabSchema`s into running Ray tasks. The frontend is being **rethought, not abandoned**: an initial standalone attempt (via Google Stitch) showed that a dashboard which *discovers* pipeline structure at run time is both harder to build and less useful than one *emitted from* the known-at-compile-time DAG, so the intended direction is now for the transpiler to emit a pipeline-specific frontend (§5.9) rather than ship a generic one from the monitoring server. A related, smaller gap sits alongside the missing runner: `hip-cargo init` does not yet scaffold any monitoring wiring into new projects, so enabling monitoring is currently a manual step — the `stokify` demonstrator does it by hand, and §9.7 proposes automating it in the templates. The principal new work proposed by this RFC — recipe→runner codegen, per-step `runtime_env`/resource wiring, and the in-memory `ObjectRef` output mechanism — is precisely the seam between the parser/resolver/IR that exist and the runner that does not.

## 5. Proposed architecture

This section describes the target shape of the transpiler and the package it emits. It is concrete enough to sanity-check against the `apis` branch, but it is not an implementation plan; where a mechanism is genuinely new or carries a dependency to validate, that is flagged rather than glossed.

### 5.1 The three-layer split and where a transpiled package sits

The runtime concerns of hip-cargo divide cleanly into three layers, and the transpiled package leans on the first two without inheriting the weight of the wrapped science stack:

- **`hip_cargo.utils.progress`** — the event vocabulary. `ProgressEvent`, the `EventType` enum (which carries `PIPELINE_STARTED`, `STEP_STARTED`, `STEP_COMPLETED`, `STEP_FAILED` alongside the per-step `STARTED`/`PROGRESS`/`COMPLETED`/`FAILED` and the in-body `LOG`/`ARTIFACT`/`METRIC` events), the `ProgressBackend` protocol, and the `track_progress()` context manager in `progress_context.py`. This layer is stdlib-only by design and therefore safe to ship in a lightweight install. A generated runner imports `track_progress` and the event types from here; it pulls in nothing heavy.
- **`hip_cargo.runtime`** — *new* (does not yet exist on `apis`; see §9). This is the layer a transpiled package depends on at run time: Ray submission helpers, the ObjectRef-chaining runner template, and the memory-mode helpers. It must remain installable without xarray/numpy/casacore — the heavy stack lives in the per-step container image, never on the orchestrator. `hip_cargo.runtime` is the seam that lets the driver coordinate a pipeline it cannot itself execute.
- **`hip_cargo.monitoring`** — the optional `hip-cargo[monitoring]` extra, already built on `apis`: `ray_backend.py` (the `ProgressAggregator` Ray actor plus `RayProgressBackend`), `dispatcher.py` (centralised WebSocket fan-out), `server.py` (the FastAPI REST + WebSocket app), and the recipe/cab introspection helpers (`recipe_parser.py`, `cab_resolver.py`, `recipe_discovery.py`). The Ray Dashboard sits beside this for cluster- and task-level analytics.

A transpiled package is an ordinary, pip-installable Python distribution. It depends on `hip_cargo.runtime` (lightweight) and, optionally at submission time, on `hip-cargo[monitoring]`. Its workers depend on whatever the cab containers carry. The key property is that the dependency weight is partitioned along the same boundary the dataflow is: the driver/orchestrator holds the light layers; the heavy layer is confined to the worker containers. A worker registers a `RayProgressBackend` via `set_backend(...)` so that the `track_progress` calls inside a step fan out to the aggregator and onward to any connected monitoring clients; a driver running without monitoring simply leaves the default `NullBackend` in place and pays nothing.

### 5.2 Recipe → runner code generation

The transpiler is a code generator, and it reuses the generators hip-cargo already has rather than inventing new ones. Three existing pieces carry most of the weight:

- **CLI surface — `generate_parameter_signature` (`utils/cab_to_function.py`).** The recipe's top-level `inputs:` block becomes the transpiled package's CLI. For each recipe input we already have a typed parameter definition (dtype, default, choices → `Literal`, info text, inline comment, list-type parser selection, hyphen → underscore sanitisation). `generate_parameter_signature` turns each into an `Annotated[...]` Typer parameter in the canonical hip-cargo style. The generated `cli.py` is therefore the same shape as any hand-written hip-cargo `cli/` module, which is what keeps it `ruff`-clean and what lets the existing tooling round-trip it.
- **Per-task bodies — the `generate_function_body` lazy-import + call pattern (`utils/cab_to_function.py`).** Each cab declares `command: pkg.core.mod.fn`; `generate_function_body` already knows how to split that into an import path and a function name, emit a lazy `from pkg.core.mod import fn as fn_core`, and emit a named-argument call site. The transpiler reuses exactly this — the import + call is the *entire* contract a cab exposes (per §2.3, the wrapper already absorbed the tool's quirks). The one adaptation is *where* the import lands: in the transpiled package the lazy import is emitted **inside the `@ray.remote` task body**, so it executes inside the worker container, not on the driver (§5.3). The container-fallback `try/except ImportError → run_in_container` branch that `generate_function_body` emits for image-bearing cabs is not needed here, because containerisation is handled structurally by Ray's per-task `runtime_env`; the transpiler emits the simpler direct-call form.
- **Events — `track_progress`.** The runner wraps the pipeline in a `PIPELINE_STARTED`/pipeline-level scope and each step submission in `STEP_STARTED`/`STEP_COMPLETED`/`STEP_FAILED`. Inside a task body, the core function can additionally open its own `track_progress(worker_name=...)` block to emit `PROGRESS`/`METRIC`/`ARTIFACT` events. No new event plumbing is required; the vocabulary on `apis` already covers pipeline- and step-level events.

The transpiler is thin precisely because these three generators already exist and already produce hip-cargo-shaped Python. Its novel job is the *wiring between* them — the DAG ordering, the ObjectRef chaining, and the per-step `runtime_env`/resource decoration described next.

### 5.3 Per-step `@ray.remote` wiring

Each recipe step becomes one `@ray.remote`-decorated function. The decorator carries two pieces of per-step configuration lifted from the cab and the recipe:

- **`runtime_env`** — built from the cab's declared container `image` (mapped to Ray's `runtime_env` `image_uri`), plus `env_vars` (e.g. thread caps such as `OMP_NUM_THREADS=1`) and `run_options` (e.g. `--cap-drop=ALL`, `--shm-size`, read-only scratch bind mounts). This is what makes the orchestrator able to coordinate a step whose code it has not installed: the step runs in its cab's image. **Dependency to validate:** Ray marks the per-task `runtime_env` `image_uri` as *experimental* upstream. This is a load-bearing assumption of the whole design and is called out as such (§1, §8, §11); it is a dependency we must verify on the target Ray version, not a finished mechanism.
- **Resources** — `num_cpus` / `num_gpus` / `memory` declared *per step* on the decorator, sourced from per-step resource hints (a new decorator/cab-schema field; §9). Resources are therefore a property of each step rather than of the recipe as a whole, which matches how heterogeneous radio-astronomy pipelines actually consume a cluster (a cheap `init` next to a GPU-hungry `image`). Nested-resource budgeting — a step that itself spawns an internal worker pool against the same cluster — remains a tuning concern (§8).

Critically, **the heavy import lives inside the task body**, inside the container. The decorator and its `runtime_env` are evaluated on the driver (cheap, string-valued config); the `from stokify.core.process import process` line only ever executes inside the worker, where `process`'s dependencies are present. This is the lightweight-install pattern: the driver imports `ray` and references `xr.Dataset` only as a return annotation (a name, not a materialised object), never the science stack itself.

### 5.4 In-memory ObjectRef dataflow and the driver-never-materializes principle

Steps are chained by Ray ObjectRef, not by passing datasets through the driver:

```
init.remote()  -> ref0
process.remote(ref0) -> ref1
image.remote(ref1)   -> ref2
```

When `process.remote(ref0)` is called, Ray resolves `ref0` to the actual `xr.Dataset` *inside the `process` worker* before the body runs; the driver never deserialises it. The driver holds only opaque `ObjectRef` handles and shuttles them from one `.remote(...)` call to the next. An intermediate `xr.Dataset` is therefore deserialised exactly once, inside the single containerised worker that consumes it — which is the structural reason the orchestrator (and the lightweight-installed package on the driver) never needs the heavy stack. The runner deliberately does **not** call `ray.get(...)` on intermediate refs; a terminal `ray.get` exists only for a final result or for debugging. Because the demonstrator is a single package backed by a single container image across all three steps, the `xr.Dataset` serialised by one worker and deserialised by the next is deserialization-safe (same library versions on both ends). Steps that genuinely produce on-disk products still write them via declared filesystem outputs; the ObjectRef path is for the *intermediate* objects that would otherwise round-trip through disk.

### 5.5 The two memory modes

The mode controls what an upstream step hands to its successor across the ObjectRef boundary. It flows from the recipe, through the runner, into each step call as a `Literal["greedy", "conservative"]`. The static return type of every step is `xr.Dataset` regardless of mode — the mode changes the *kind* of dataset, not the signature.

- **`memory_greedy`** — the step returns a **reified, plasma-resident** `xr.Dataset`: the array data lives in Ray's plasma object store and is handed to the next worker directly. This *truly bypasses disk* between steps. The cost is plasma residency (hence the `--shm-size` in the `run_options`), which is why it is a mode and not the only behaviour.
- **`memory_conservative`** — the step returns a **small, lazily store-backed** `xr.Dataset`, e.g. `xr.open_zarr(...)` **without Dask**: a thin handle whose reads resolve to a shared store on access. This *defers* disk I/O to that store rather than eliminating it, so conservative mode assumes a store every worker can reach (a shared mount or an object store). It is not a free lunch; it trades plasma pressure for the assumption of a reachable shared store.

Both modes share the win that matters for pipeline throughput: **neither writes an intermediate product to disk as a materialised file passed by path**. Greedy bypasses disk entirely; conservative defers reads to a store but still does not round-trip a written intermediate through the recipe's data flow. The branch between the two lives inside the `core/` function (it chooses how to construct its return), which keeps the runner and the static signature uniform.

### 5.6 Lightweight-install calling pattern (canonical)

The following sketch is the shape the runner is built around. The driver imports only `ray` and (for the type annotation) `xarray`; the science package is imported inside the task, inside the container.

```python
import ray
import xarray as xr

ray.init()  # or ray.init(address="auto") on a cluster

CONTAINER_ENV = {
    "container": {
        "image": "registry.example.com/stokify-worker:latest",
        "run_options": [
            "--cap-drop=ALL",
            "--shm-size=8g",                 # plasma + numpy temp buffers
            "-v", "/scratch:/scratch:ro",    # shared storage, read-only
        ],
    },
    "env_vars": {"OMP_NUM_THREADS": "1", "MKL_NUM_THREADS": "1"},
}

@ray.remote(runtime_env=CONTAINER_ENV, num_cpus=4)
def step(payload: dict) -> xr.Dataset:
    # imported INSIDE the container — present in the image, not on the driver
    from stokify.core.process import process
    return process(**payload)

ref = step.remote({"ms_path": "/scratch/obs.ms", "band": 3})
```

`CONTAINER_ENV` is what the transpiler synthesises per step from the cab's `image` + `env_vars` + `run_options`; `num_cpus` is the per-step resource hint; the in-body import is the lazy-import pattern from §5.2; and `ref` is the opaque handle the runner threads forward without ever calling `ray.get` on it.

### 5.7 IR sketch

The transpiler extends hip-cargo's existing "one CST walk, multiple consumers" discipline (`utils/spec.py`, where `ModuleSpec`/`CommandSpec`/`ParamSpec` already feed both `generate-cabs` and `generate-schemas`). A recipe is a second neutral artifact alongside the per-module IR, capturing the *facts of the recipe* without cab- or runner-specific shaping. At a high level:

- **`RecipeSpec`** — top-level recipe inputs (the future CLI surface), the ordered list of `StepSpec`s, the recipe-wide `memory_mode` default, and any shared-store configuration the conservative mode needs.
- **`StepSpec`** — one step: the cab reference it resolves to (`command` → import path), its ordered upstream dependencies (the steps whose ObjectRefs feed it), its per-step parameter **bindings** (each a literal value, a `=recipe.x` namespace reference, or a `{recipe.x}` interpolation — and nothing else; the formula-DSL cut of §6 means the binding side is finite and statically resolvable), its `runtime_env` (image + `env_vars` + `run_options`), and its resource request (`num_cpus`/`num_gpus`/`memory`).

This is deliberately *neutral*: it records ordering and bindings, not Ray syntax. Two consumers shape it — the runner generator (ObjectRef chaining, `@ray.remote` decoration) and the CLI generator (`generate_parameter_signature` over the recipe inputs). It overlaps with the monitoring-side `RecipeDAG`/`RecipeStep` model already in `monitoring/recipe_parser.py`, and the intended architecture is a **single parser front-end** rather than two. One front-end parses the recipe YAML, classifies each binding (literal vs. `=recipe.x` reference vs. `{recipe.x}` interpolation), extracts references, and builds the step edges — work `recipe_parser.py` already does — and feeds two consumers: the monitoring view that *visualises* a DAG and the codegen view (`RecipeSpec`) that *generates code*. The transpiler adds two things on top of that shared front-end: validation that the recipe stays within the restricted subset (§6), and resolution of restricted bindings to concrete Python expressions. We should not build two parsers for one YAML format; the open question (§11) is the precise shape of the shared front-end, not whether to share it.

### 5.8 The `stokify` demonstrator

The concrete target is the `stokify` package scaffolded via `hip-cargo init`, with three steps each returning an `xr.Dataset`: `init` (read a measurement set), `process` (coherencies → image-ready Stokes visibilities), `image` (grid + image the Stokes visibilities). The transpiled output is three hand-written-then-codegen-validated modules:

- **`tasks.py`** — one `@ray.remote` function per step (`init`, `process`, `image`), each decorated with its synthesised `runtime_env` (the single `stokify` worker image across all three) and its per-step resources. Each body is the lazy-import + named-call pattern of §5.2: `from stokify.core.init import init as init_core; return init_core(...)`, with the `memory_mode` threaded in as a `Literal["greedy","conservative"]` argument.
- **`runner.py`** — calls `ray.init()` once (or `ray.init(address="auto")` on a cluster), registers a progress backend if monitoring is active, opens the `PIPELINE_STARTED` scope, then chains the ObjectRefs: `ref0 = init.remote(...)`; `ref1 = process.remote(ref0, ...)`; `ref2 = image.remote(ref1, ...)`, emitting `STEP_STARTED`/`STEP_COMPLETED`/`STEP_FAILED` around each submission. It holds only refs; it does not `ray.get` the intermediates. A terminal `ray.get(ref2)` (or a filesystem product from the `image` step) yields the final result.
- **`cli.py`** — a Typer app generated from the recipe's top-level `inputs:` via `generate_parameter_signature`, parsing CLI arguments into the recipe inputs and invoking `runner.py`. Its dependency footprint is `ray` + `hip_cargo.runtime` + Typer — lightweight; the heavy stack stays in the worker image.

Building `stokify` fresh, to the `flavour: python` import-and-call contract from the start, lets the in-memory ObjectRef model be exercised end-to-end without first refactoring a heavy existing package (the pfb-imaging Ray-ownership refactor of §1/§9 is a *future-integration* cost, not a precondition here). The first milestone is structural: the generated package installs lightweight, the CLI builds, the generated Python is `ruff`- and `bandit`-clean, and the DAG/bindings resolve — with live execution on a real measurement set kept as a separate, opt-in milestone.

### 5.9 Frontend emitted by transpilation

The monitoring frontend is the part of the original vision the rest of this RFC has so far underplayed, and transpilation changes its shape for the better. The key observation is that **at transpile time the whole pipeline structure is known statically**: the transpiler holds the resolved DAG — steps, edges, per-step parameter schemas (from the cabs), resource requests, container images, and the memory mode — fully validated before any code runs. A frontend built from that structure does not have to *discover* the pipeline; it can be *generated from* it.

Concretely, transpilation lets the frontend be a compile-time artifact rather than a run-time reconstruction:

- The DAG view (a React Flow graph, in the direction explored on `apis`) is generated from known node/edge data baked in as static JSON, not assembled from API calls on first load.
- The per-step parameter forms are pre-typed components generated from the resolved cab schemas — the same `CabParam` dtypes the cab YAML already carries — rather than dynamically rendered from a schema fetched at run time.
- The metric-chart layout can be arranged ahead of time for the metrics each step is known to emit, where those metrics are declared on the step (the `track_progress`/`tracker.metric(...)` calls in a `core/` function are inspectable at transpile time).
- The pipeline topology ships embedded in the frontend, so a late-joining client sees the full graph immediately rather than waiting for it to stream over the WebSocket.

The division of labour is clean: the **structure** is compiled in, while the monitoring *server* (the FastAPI app on `apis`, §4) still owns everything genuinely dynamic — live progress streaming, metric updates, and job control (kill/relaunch a step with edited parameters). This is a real architectural improvement over the original dashboard, where the frontend had to parse recipes and poll APIs to learn what it was looking at; here the structure is settled at compile time and only the live state flows at run time.

This is the concrete delivery mechanism the §3 lineage points at, and it is **not yet built** — a direction the transpiler enables, not a deliverable of the first spike. It connects back to the `init` template work: §9.7 proposes that `hip-cargo init` scaffold a monitoring view as part of the template, and that `hip-cargo transpile` optionally emit a pre-built, pipeline-specific monitoring frontend alongside the runner. The React frontend itself is out of scope until the RFC is accepted and the runner shape is settled; what matters for this proposal is that the transpiler's compile-time knowledge of the DAG makes that frontend cheaper and more specific than the run-time-discovery design it replaces.

## 6. What we deliberately exclude

The restricted subset is defined as much by what it refuses as by what it admits. Each exclusion below ties back to one of two principles established in Section 2: the security/auditability boundary (no surface for arbitrary code; everything must be analysable by `ruff`/`bandit`), or wrapper standardization (the need was already absorbed once, in `core/`, so the transpiler need not carry it). These are not deferred features; they are commitments.

- **No shell steps / arbitrary commands.** This is the security boundary directly. Cabs are Python callables, so a shell escape is both unsafe on shared HPC and unnecessary. There is nowhere in the grammar to place a command string.

- **No wranglers / output-parsing regex.** Unnecessary. Core functions write structured products to declared output paths (and may also return typed values); a wrapped tool's messy stdout/stderr conventions were already absorbed in `core/`. There is no unstructured stream left to scrape, so there is no regex to run.

- **No formula DSL beyond plain references and f-string interpolation.** The subset admits only namespace references (`=recipe.x`) and `{recipe.x}` interpolation. Explicitly out: `=IF`, `=IFSET` (all arities), arithmetic, `=GLOB`, nested substitutions, and `${self:...}`. This is the static-analysability cut from §2.2: anything the DSL would compute at run time is opaque to `ruff`/`bandit`. As noted in §2.2, the canonical SARA recipe uses `=IF`, `=IFSET`, and arithmetic, so the demonstrator is a flattened version with those resolved by hand.

- **No alias broadcast (`*.x`).** Replaced by explicit per-step bindings. A glob that sprays one recipe-level value across every matching step parameter is convenient but hides data flow; the SARA recipe uses it (e.g. `aliases: ['*.output-filename']`). This is the static-analysability boundary from §2.2 again: for an auditable artifact, every binding a step receives should be visible at that step's call site, so the transpiler requires them written out.

- **No `_use` / `_include` modularity beyond hip-cargo cab references.** Recipe-level composition and reuse are expressed through Python imports in the generated package, not through a YAML include/merge mechanism. The only `_include` the transpiler honours is the cab reference itself, which resolves to an importable function. This is the static-analysability boundary from §2.2: a YAML merge layer is run-time-resolved and opaque to `ruff`/`bandit`, whereas Python imports are not.

- **No `assign_based_on` / preamble / epilogue.** These are run-time control-flow and environment-mutation hooks. They reintroduce the very dynamism §2.1/§2.2 exclude, and the legitimate setup a step needs has already been absorbed into its `core/` function or expressed through its container `runtime_env`.

- **No CASA flavour, no binary flavour.** The transpiler consumes only typed Python functions in hip-cargo-shaped packages (`flavour: python`). A CASA task or a bare binary has not been normalised into a typed callable, so the runner — which only does *import + call* — has nothing to invoke; such tools must be wrapped first, at which point they enter through the standard door like everything else.

- **No `opts` runtime namespaces (`config.*`, `info.*`).** These expose stimela's run-time configuration and introspection namespaces into recipe expressions. They are inherently dynamic and unavailable to a static analyser; admitting them would mean a binding's value again depends on run-time state that `ruff`/`bandit` cannot see. The information a step legitimately needs is passed as an explicit, typed argument instead.

Taken together, these exclusions are why the transpiler can be thin: each is either the auditability boundary holding firm or a need the wrapper layer already absorbed. Re-admitting any of them would reintroduce the run-time dynamism the auditability claim depends on excluding. The result is a tool that does far less than stimela by design, which is the point for the subset of users in §2.

## 7. Pros

### Security rooted in wrapper discipline, not policy machinery

The strongest argument for `transpile` is that its security posture is a *consequence* of the restricted input grammar rather than something the transpiler must enforce at runtime. Because every external tool has already been wrapped once into hip-cargo's three-layer shape — `cli/` (Typer + `Annotated`), `core/` (plain Python that absorbs the tool's quirks), `cabs/` (generated schema) — the transpiler never re-implements a cab's core function. It emits a *thin runner* that imports an already-importable plain Python function (flavour: `python`) and calls it with named arguments. There is no shell flavour, no formula DSL beyond `=recipe.x` refs and `{recipe.x}` interpolation, no wranglers, and no runtime `opts` namespaces. The grammar therefore exposes no shell- or formula-injection surface, and the generated Python passes `ruff` and `bandit`.

The honest bound on this claim matters: a clean `bandit` run is a **meaningful negative result given the input grammar** — it confirms the generated runner contains none of the patterns `bandit` flags, on code whose shape the grammar constrains — but it is **not** a proof of behavioural safety and **not** whole-program data-flow tracing. The core functions a runner calls remain arbitrary Python; their safety is the wrapper author's responsibility, audited once, not the transpiler's. What `transpile` buys is that the *orchestration glue* — historically the part of a pipeline where injection and surprising shell composition live — is reduced to statically inspectable, generated code.

### Reproducibility via the container image (with a caveat)

Each step is wrapped in `@ray.remote(runtime_env={image_uri, env_vars, run_options}, num_cpus=...)`, so the execution environment is a named container image rather than the caller's ambient Python. For the `stokify` demonstrator, a single package compiles to a single image used across all three steps, which makes the environment one auditable artifact.

The caveat must be stated plainly: pinning an image by *tag* (the current default, e.g. `:apis`) is **not** reproducible — tags are mutable and can be re-pushed. True reproducibility requires pinning a **digest** (`...@sha256:...`). The transpiler should support and encourage digest pinning; tag-based references are a convenience for development, not a reproducibility guarantee.

### Smaller maintenance surface

The transpiler is thin *by construction*. Because the wrapper already absorbed each tool's quirks, the transpiler needs no policy engine, no parameter-passing flavours, no wrangler regexes, and no formula evaluator. The principal new code is recipe→runner codegen, per-step `runtime_env`/resource wiring, the in-memory `ObjectRef` output mechanism, and replacing the current placeholder submit path (today a fragile stimela-run string builder) with a direct `hip_cargo.runtime` submit call — a bounded surface to test and review, layered on the ~70%-built `apis` branch rather than green-field.

### Alignment with SARAO's Ray migration

The output is an installable, Ray-orchestrated Python package, which lands directly on the trajectory SARAO is already investing in. Mature recipes that today run under stimela can be hardened into artifacts that target the same scheduler and cluster tooling the rest of the migration assumes, rather than introducing a parallel orchestration runtime.

### Static analysability

Because the runner is ordinary generated Python, the whole standard static-analysis toolchain applies — `ruff` for style/correctness lint, `bandit` for the security-pattern scan above. This is a real, if bounded, property: the orchestration layer is amenable to the same gates as any other first-party module, which is not generally true of a string-templated or DSL-interpreted recipe.

### Observability via existing infrastructure

hip-cargo already ships a monitoring server (FastAPI REST + WebSocket, with a Ray progress backend in `monitoring/`). A transpiled package slots into this without new plumbing, and Ray's own Dashboard provides task/actor/resource visibility for free. Operators get per-step progress and cluster-level introspection out of the box.

### In-memory pipelining as a performance win

In `memory_greedy` mode, each step returns a reified, plasma-resident `xr.Dataset` passed to the next step as a Ray `ObjectRef`. The driver-never-materializes principle holds — the driver carries only opaque refs; the `xr.Dataset` is deserialized only inside the consuming containerized worker — so intermediate results genuinely bypass disk between steps. For an I/O-bound pipeline like `init → process → image`, eliminating intermediate writes/reads is a concrete latency and storage win, and it is what allows the lightweight-installed driver to avoid the heavy stack entirely.

## 8. Cons and risks

### Ecosystem fragmentation

`transpile` adds a second tool to the radio-astronomy workflow story. Practitioners already learn stimela to develop pipelines; this introduces a separate hardening target with its own grammar, failure modes, and mental model. Even though the relationship is intended to be sequential (develop in stimela, harden mature recipes with hip-cargo), in practice teams will carry both, and the cognitive and documentation cost of "two tools" is real and should not be minimized.

### Migration friction: recipes must be rewritten, not ported

This is not a transparent compiler over arbitrary stimela recipes. A recipe must be **rewritten into the restricted subset** before it can be transpiled. Anything relying on the deliberate cuts — shell/arbitrary commands, wranglers, the full formula DSL (`=IF`, `=IFSET`, arithmetic, `=GLOB`, nested substitutions, `${self:...}`), alias broadcast (`*.x`), `_use`/`_include` beyond cab refs, `assign_based_on`/preamble/epilogue, CASA/binary flavours, `config.*`/`info.*` namespaces — must be flattened by hand into the restricted form, or pushed down into a cab's `core/` function. For a mature, branchy recipe this flattening is non-trivial up-front labour, and it is labour that produces a *less* expressive recipe. The demonstrator (`stokify`) sidesteps this by being purpose-built in the subset from the start; real existing recipes will not be so cooperative.

### Dependence on Ray

The proposal couples pipeline execution to Ray, and to a specific Ray capability that is not finished:

- **Experimental `image_uri`.** Per-task `runtime_env` `image_uri` is **experimental upstream**. It is a dependency to *validate*, not a settled foundation; if its semantics or availability shift, the per-step container model shifts with it.
- **Unbuilt submit path.** The current submit path is a placeholder stimela-run string builder; replacing it with a direct `hip_cargo.runtime` submit call (per §9.6) is **unbuilt new work**, part of the proposed new surface rather than a cleanup of existing code. Until that replacement lands, the Ray-native dispatch story is not exercised end-to-end.
- **Version skew.** Three places must agree on a Ray version: the cluster, the transpiler, and the generated package. Skew between any pair is a plausible and annoying failure mode, especially as the package is meant to outlive the recipe author's session.
- **Non-Ray HPC sites.** Many SARAO-relevant HPC environments are batch-scheduler shops (Slurm/PBS) with no standing Ray cluster. The deployment story there — standing up Ray on an allocation, mapping Ray resources onto the scheduler's — is real work the transpiled artifact does not solve on its own.

### Limited expressiveness of the restricted subset

The same cuts that make the grammar auditable make it narrow. Recipes that legitimately need conditional steps, computed parameters, globbing, or per-target broadcast cannot be expressed and must move that logic into a cab's core function (changing where the logic lives, and its testability) or stay in stimela. The subset is a deliberate floor, not a temporary limitation, and some genuinely reasonable pipelines will not fit it.

### Memory modes: only `greedy` truly bypasses disk

The two memory modes are not equivalent. `memory_greedy` returns a reified, plasma-resident `xr.Dataset` and genuinely avoids disk between steps. `memory_conservative` returns a **small, lazily store-backed** `xr.Dataset` (e.g. `xr.open_zarr(...)` without dask) — it **defers** disk reads to a shared store rather than eliminating them, and it therefore **assumes a store every worker can reach**. On a site without such shared storage, `conservative` mode's premise breaks. Both modes avoid *writing* intermediates, but the "disk bypass" performance story belongs to `greedy` alone, and `greedy` trades that for plasma memory pressure that must be budgeted.

### Cross-container `ObjectRef` deserialization for heterogeneous pipelines

The clean `ObjectRef`-chaining story holds because `stokify` is a **single package → single image**: an `xr.Dataset` serialized in one step deserializes safely in the next because both run the same environment. This dodges the hard case rather than solving it. A **heterogeneous** pipeline — different steps in different images with different `xarray`/`numpy`/pickle stacks — reintroduces the classic cross-container deserialization fragility (pickle protocol and library-version mismatches across the boundary). Transpiling real multi-tool pipelines will have to confront this, and the demonstrator does not exercise it.

### Nested-resource budgeting on Ray

Each step declares `num_cpus=...`, but the core functions inside containers may themselves be parallel (their own thread pools, BLAS threads, internal Ray usage). Reconciling a step's declared Ray budget with the actual resource appetite of the wrapped tool is an unsolved budgeting problem; misdeclaration leads to oversubscription or idle reservations on shared clusters.

### Small-team sustainability

This is built and maintained by a small team — currently effectively the stimela maintainer who is authoring this RFC. The transpiler is thin, which helps, but it still depends on tracking an experimental Ray feature and on the wrapper discipline being upheld for every tool. Bus-factor and long-term maintenance are genuine risks, and the proposal's value degrades quickly if the wrapper standardization is not sustained.

### Adjacent to stimela, not a replacement

To be explicit and fair: this does **not** supersede stimela. stimela is the de-facto general-purpose tool for *developing* pipelines, and its universality — shell flavours, wranglers, the formula DSL, broadcast — is a reasonable design with real costs, not a flaw to be corrected. `transpile` is a hardening target for *mature* recipes, adjacent and sequential. If a reader comes away thinking hip-cargo aims to replace stimela, the framing has failed; the honest scope is narrower and the value proposition is contingent on that narrowness.

## 9. Required changes to hip-cargo

This proposal builds on the `apis` branch, which is roughly 70% of the way to what `transpile` needs: the three-layer wrapper shape (`cli/` Typer+`Annotated`, `core/` plain Python, `cabs/` generated schema), the `@stimela_cab`/`@stimela_output` decorators, the `flavour: python` cab convention with a `command:` pointing at an importable function (e.g. `command: hip_cargo.core.generate_function.generate_function`), the shared IR (`ParamSpec`/`CommandSpec`/`ModuleSpec` via `parse_module`), and the `StimelaMeta` Annotated-metadata container. The changes below are additive. They do not touch the existing `generate-cabs` / `generate-function` / `generate-schemas` paths, and they do not require re-implementing any cab's core function — the transpiler emits a thin runner that imports and calls those functions by name.

The principal new work is, in order of conceptual weight: (8.1) a new *output category* for in-memory `ObjectRef`-backed datasets and the memory-mode contract that governs them; (8.2) the `hip-cargo transpile` command and its codegen; (8.3) decorator extensions carrying per-step resource and `runtime_env` hints; (8.4) a lightweight-installable `hip_cargo.runtime` subpackage; (8.5) packaging conventions; (8.6) replacing the stimela-run submit path; and (8.7) `hip-cargo init` template changes. We close by noting the pfb-imaging Ray-ownership refactor as an external precondition for *future* heavy-package integration — explicitly not needed for the stokify demonstrator.

### 9.1 In-memory `ObjectRef` outputs: a new output category

Today hip-cargo models exactly one kind of output: a filesystem artifact. `@stimela_output(name=..., dtype="File"|"Directory"|"MS", ...)` declares a path the cab writes; `runner._resolve_mounts` reads those declarations (plus path-typed inputs) and turns them into bind mounts — outputs `rw`, inputs `ro`. The whole mount machinery in `utils/runner.py` is organized around the assumption that a step communicates with the next step *through the filesystem*, and that hip-cargo's job is to make the right host directory visible inside the container.

The transpiler needs a second, orthogonal output category: a value that lives in the Ray object store and is passed to the next step *by reference*, never touching a mount. Concretely, each stokify step returns an `xr.Dataset`, and we want `init.remote() → ref → process.remote(ref) → ref → image.remote(ref)` with the dataset materialized only inside the consuming worker. There is no host path to bind, so the existing `_resolve_mounts` logic must *not* fire for these outputs; equally, `preflight_remote_must_exist` and the implicit-output mount pass are irrelevant to them.

The minimal way to express this is a new declaration that sits beside `@stimela_output` rather than overloading it. The strawman is an `@stimela_objectref_output` decorator (name open for discussion) recording `{name, dtype: "xr.Dataset", chained: True}` on the function, and a matching cab-schema marker — most naturally an `outputs.<name>.dtype: "ObjectRef"` (or `dtype: "xr.Dataset"` with `metadata: {objectref: true}`, to stay inside Stimela's finite top-level field set the same way `tunable` rides under `metadata`). The transpiler reads this marker to decide chaining: an `ObjectRef` output of step *N* becomes a positional/named `ObjectRef` *input* of step *N+1*, wired as a Python value in the generated runner. It contributes no mount and no path preflight. The static Python signature of the consuming core function still declares the argument as `xr.Dataset` (the worker receives a deserialized dataset, not a ref — the ref lives only in the driver); the runner is responsible for the `ref → dataset` boundary, which is exactly Ray's `.remote(ref)` deserialization-on-task-entry semantics. Because all three steps ship in one image, the dataset class and its codecs are identical on both sides, so deserialization is safe — this is the load-bearing reason the demonstrator uses a single package and a single image.

An honest caveat: `xr.Dataset` is not a trivially Ray-serializable object in general. Whether a given dataset round-trips cleanly through the object store depends on what backs its arrays (in-memory NumPy vs. a dask graph vs. a lazy store handle). That dependence is precisely what the memory-mode contract pins down.

#### Memory modes

The recipe selects one of two modes, threaded unchanged through the runner into every step call as a `Literal["greedy", "conservative"]` argument:

- **`memory_greedy`** — the step returns a fully reified, plasma-resident `xr.Dataset` (NumPy-backed, no dask graph, no lazy handles). The next step's worker deserializes a concrete dataset directly out of the object store. This genuinely bypasses disk for intermediates: nothing is written and nothing is re-read. The cost is plasma residency — the intermediate must fit (with spilling) in the cluster's object-store budget.
- **`memory_conservative`** — the step returns a *small*, lazily store-backed `xr.Dataset`: e.g. the handle from `xr.open_zarr(store_uri)` opened **without dask**, so the serialized object is the lazy dataset descriptor plus coordinates, not the bulk arrays. This does **not** eliminate disk; it *defers* reads to a shared store that every worker can reach (e.g. a cluster filesystem or an object bucket), and it relies on each step having persisted its bulk output to that store. It trades the plasma-budget risk of greedy mode for an assumption about shared-store reachability and latency.

Both modes share the invariant that hip-cargo cares about: **neither writes a throwaway intermediate to local disk between steps.** They differ in *where* the bytes live (plasma vs. shared store) and therefore in their failure modes. The core function carries the branch internally — same signature, same `xr.Dataset` return type, an `if mode == "greedy": ... else: ...` inside — so the static contract the transpiler reasons about is invariant. We are deliberately not trying to make the mode a type-level distinction; keeping it a runtime `Literal` keeps the IR, the cab schema, and the generated signatures unchanged regardless of mode. The two modes are best understood as a knob the *recipe author* sets per run, not per step, at least for the demonstrator; per-step modes are a possible extension we are not committing to.

### 9.2 The `hip-cargo transpile` command

A new CLI command, registered in `cli/__init__.py` alongside the existing ones, with the core implementation in `core/transpile.py`. Signature sketch:

```
hip-cargo transpile RECIPE.yml --out-package <dir> [--memory-mode greedy|conservative]
```

It consumes a recipe in the *restricted grammar* defined in section 6 (cab `_include`s, `steps` with `cab:` + `params:`, `=recipe.x` references and `{recipe.x}` f-string interpolation only — no wranglers, no formula DSL beyond those two forms, no aliases, no `assign_based_on`/preamble/epilogue, no shell/CASA flavours, no `opts` runtime namespaces). It resolves each step's `cab:` to its generated cab YAML (reusing `monitoring/cab_resolver.py`'s `_include` resolution and `recipe_parser.py`'s DAG extraction, which already classify `=recipe.*` bindings and build the step edge list), reads each cab's `command:` and `flavour: python`, reads the new `ObjectRef` output/input markers, and emits an installable Python package whose `runtime/_pipeline.py` (name tentative) is the thin runner.

The runner is mechanical. For each step it emits a `@ray.remote` task whose body does nothing but `from <cab.command.module> import <func>; return <func>(**named_args)`. It wires `=recipe.x` references to driver-level parameters, `{recipe.x}` interpolations to f-strings over those parameters, and `ObjectRef` chaining to `ref = step_n.remote(...)` / `step_{n+1}.remote(ref, ...)`. It threads the memory mode into every call. The transpiler is thin precisely because the wrapper already absorbed every quirk at the `core/` layer (§2.3, wrapper standardization) — it needs no policy machinery, no parameter-passing flavours, no wrangler regexes, no formula evaluator. The emitted package is formatted with the same `ruff format`/`ruff check --fix` pass `generate-function` already shells out to, and is expected to pass `bandit` cleanly. As §2.2 states, a clean bandit run is a meaningful *negative* result given the restricted input grammar (there is no shell or formula injection surface for it to find), not a proof of behavioural safety and not whole-program data-flow analysis. The auditable artifact is the generated package source, checked in and diffable.

### 9.3 Decorator extensions for per-step resources and runtime_env

Each step is wrapped as `@ray.remote(runtime_env={...}, num_cpus=..., ...)`. Those values have to come from somewhere declarative. The natural home is the existing decorator/cab-schema metadata channel, extended (not replaced):

- **Resources** — `num_cpus`, `num_gpus`, `memory`, and optional `resources={...}` custom labels (relevant for SARAO HPC scheduling). These belong on the cab, since they are a property of the wrapped tool, with optional per-step override in the recipe. Strawman: a `resources` block carried under the cab's `metadata` (the same dict that already carries `rich_help_panel` and `tunable`), surfaced in Python via a new `StimelaMeta`-style field or a `@stimela_resources(...)` decorator.
- **`runtime_env`** — the per-task container `image_uri`, plus `env_vars` and `run_options`. The image is today a single `image:` field on the cab, sourced from `_container_image.py`'s `CONTAINER_IMAGE` (currently `ghcr.io/landmanbester/hip-cargo:apis` — a mutable dev tag; see the digest-pinning caveat in §7). The transpiler maps `image:` → `runtime_env={"image_uri": ...}` and merges any declared `env_vars`/`run_options`.

A standing risk we must flag rather than paper over: **Ray's per-task `runtime_env` `image_uri` is an experimental upstream feature.** It is a dependency to validate early, not a finished foundation. If it proves unusable, the fallback is a single image for the whole job (acceptable for stokify, since one package → one image already) with per-step resource requests still honored — but the per-step-image story is the part most likely to need rework, and the RFC should not assume it.

### 9.4 The `hip_cargo.runtime` subpackage

A new subpackage holding everything the *generated* package imports at orchestration time:

- Ray submit helpers (cluster connect/`ray.init` handling, job submission, ref collection) that replace the stimela-run submit endpoint (8.6).
- The `ObjectRef`-chaining runner *template* — the codegen target and the helper functions it calls (e.g. a `chain(steps, mode)` driver loop, ref-threading utilities).
- Memory-mode helpers: small functions a `core/` author can call inside their mode branch (e.g. a `conservative_open(store_uri)` that wraps `xr.open_zarr(..., chunks=None)` to guarantee no-dask, and a `greedy_reify(ds)` that forces NumPy backing and drops lazy handles before return). Keeping these in `hip_cargo.runtime` rather than re-deriving them in every project is what keeps the per-step branch in user code to a couple of lines.

Critical constraint: `hip_cargo.runtime` must stay **lightweight-installable**. It imports `ray` (already an extra under `monitoring`; transpile likely warrants its own `ray`/`transpile` extra) but it must **not** import `xarray`, `numpy`, or any step's heavy stack. This is the driver-never-materializes principle in packaging form: the driver holds only opaque `ObjectRef`s, an `xr.Dataset` is deserialized only inside a containerized worker, so the orchestration layer — and the lightweight-installed package and its driver — never need the heavy dependencies. The memory-mode helpers that *do* touch `xarray` (`conservative_open`, `greedy_reify`) are the exception and must be import-guarded or split so that importing `hip_cargo.runtime` for submission does not drag in `xarray`; they run inside the worker, where the heavy stack is present.

### 9.5 Packaging conventions

The generated package follows the split the runtime enforces:

- **Lightweight install** — the package's own dependencies are `hip-cargo[ray]` plus whatever the driver genuinely needs (typically nothing heavy). This is what gets installed on the submitting host / login node, and it is what an auditor reviews.
- **Heavy deps in the per-step container image** — `xarray`, `numpy`, `casacore`, the gridder, and the rest live in the image referenced by `runtime_env.image_uri`, not in the package's `pyproject.toml`. The image is the unit of heavy-dependency provisioning; the package is the unit of orchestration and audit.

This mirrors hip-cargo's own layout, where `core/` modules lazy-import heavy work and the CLI stays thin, and it is the reason a lightweight driver can orchestrate a heavy pipeline at all.

### 9.6 Replacing the stimela-run submit endpoint

The current monitoring path launches recipes by shelling out to `stimela run` and observing it (`monitoring/ray_backend.py`, the `FakeJobClient` test mock, etc.). For transpiled recipes this indirection is removed: the transpiled package *is* the runnable artifact, so submission becomes a direct call into `hip_cargo.runtime`'s submit helper that invokes the generated driver (`ray job submit` against a cluster, or an in-process `ray.init` for local runs). This eliminates a fragile, hard-to-audit surface — parsing stimela's stdout, depending on its process lifecycle — and replaces it with a Python function call whose inputs are the recipe's typed parameters. The existing dispatcher/WebSocket fan-out in `monitoring/` can be retained to observe the transpiled run; only the *launch* mechanism changes. (Stimela remains the right tool for *developing* the recipe; this only changes how a *matured, transpiled* recipe is executed — adjacent and sequential, not a replacement.)

### 9.7 `hip-cargo init` template changes

For a scaffolded project to be transpile-ready out of the box, the `init` templates (`src/hip_cargo/templates/`, driven by `core/init.py`'s strict post-generation sequence) need to emit the *stokify shape*:

- A multi-command project (`--cli-mode multi`) whose `core/` functions return `xr.Dataset` and accept the memory-mode `Literal` and, where chained, an upstream `xr.Dataset` argument.
- The new (strawman) `ObjectRef`-output declarations of §9.1 on the step decorators, so `generate-cabs` emits the `ObjectRef` markers and the recipe is immediately transpilable.
- A starter recipe under `recipes/` written in the restricted grammar (cab `_include`s, `=recipe.x` / `{recipe.x}` only), chaining the three steps by reference.
- The heavy stack (`xarray`, etc.) declared in the project's `Dockerfile`/image, not in its `pyproject.toml`, matching 8.5.

The branched single-vs-multi post-init print paths in `core/init.py` must be preserved (per the architecture rules); the stokify scaffold is a `multi` variant, not a unification of the two.

### External future precondition: pfb-imaging Ray ownership

Transpiling an *existing* heavy package such as pfb-imaging will eventually require a small refactor there (~30–50 LOC): gating `ray.init`/`ray.shutdown` on `ray.is_initialized()` and on whether the process *owns* the Ray context, so a pfb step invoked as a Ray task does not try to bootstrap or tear down a cluster it did not start. This is an **external, future-integration cost**, listed here only for completeness. It is **not** on the critical path for the stokify demonstrator, which is purpose-built to be Ray-friendly from the first commit and never calls `ray.init` inside a step.

## 10. Alternatives considered

This section records the options weighed against the proposal and why each was set aside. None is dismissed as unworkable; in several cases the alternative is a better fit for a different problem than the one this RFC targets. The recurring decision criterion is whether the option delivers the four properties the design is organised around — a statically auditable artifact, the in-memory ObjectRef/`xr.Dataset` dataflow, reuse of the ~70%-built `apis`-branch foundation (the monitoring stack, the shared IR, the existing codegen), and the leverage from hip-cargo's one-time wrapper standardization — without re-acquiring the run-time dynamism §2.1/§2.2 deliberately exclude.

### (a) Contribute stricter modes / static-analysis features upstream to stimela

**What it is.** Rather than build a separate compiler, add an opt-in "strict mode" to stimela itself: a flag that rejects shell steps, refuses the formula DSL beyond plain references, forbids wranglers and `assign_based_on`, and exposes a lint/audit pass over a recipe. Recipes that pass would gain much of the auditability argued for in §2, and the work would benefit every stimela user rather than a fork of them.

**Why not chosen (for this RFC).** This is genuinely attractive and is not foreclosed by anything here; the author is a stimela maintainer and some of these checks may well belong upstream regardless. The reason it does not satisfy *this* proposal is that a strict mode constrains stimela's *inputs* but does not change what stimela *is* at run time: a general framework that interprets a recipe structure in-process. It would not, on its own, produce the compiled artifact §1 calls for — an installable Python package you can read, `ruff`/`bandit`, version, and audit independently of the framework that emitted it. Nor would a lint pass give us the in-memory ObjectRef model: passing `xr.Dataset` between steps as Ray ObjectRefs, with the driver-never-materializes property, is an orchestration architecture, not a validation rule, and grafting Ray-native per-step `runtime_env`/ObjectRef chaining into stimela's general execution model is a far larger change than the thin runner this RFC describes. Finally, the thinness of our transpiler is bought by hip-cargo's wrapper standardization (§2.3) — every cab is already a typed `flavour: python` callable — which is a property of the hip-cargo ecosystem, not of arbitrary stimela cabs. A strict mode would still have to cope with the full range of cab flavours and parameter-passing conventions that standardization lets us ignore. The honest summary: upstream strictness and this proposal are complementary, and some checks should likely flow upstream; but a flag on a general interpreter is not a compiler to an auditable artifact.

### (b) Build atop Snakemake or Nextflow

**What it is.** Both are mature, widely used workflow managers with large communities, good provenance/reporting, native HPC scheduler integration (Slurm and others), and per-rule/per-process container support. We could express the restricted subset as a Snakemake `Snakefile` or an Nextflow workflow, transpiling the YAML into one of those instead of into a Ray package.

**Why not chosen.** Two reasons, one architectural and one about reuse. Architecturally, both Snakemake and Nextflow are fundamentally *file-graph* schedulers: a rule/process declares input and output *paths*, and the engine decides what to run by reasoning about which files exist and are stale. That model is a poor fit for the central mechanism in §1 — passing a reified, plasma-resident `xr.Dataset` between steps as an ObjectRef so that disk is bypassed entirely between steps (`memory_greedy`), with the driver holding only opaque refs. Expressing in-memory object handoff on a file-graph engine means materialising intermediates to disk (or a channel that serialises through disk), which is precisely the cost the in-memory mode exists to avoid; `memory_conservative` could be mapped onto a shared store, but `memory_greedy` could not be honoured at all. The audit story is also weaker: Nextflow processes carry shell `script:` blocks and Snakemake rules admit `shell:`/`run:` directives, so we would re-import the shell-injection surface that §2.1 closes by construction, and "audit the recipe" would again mean "audit arbitrary code." On reuse: adopting either engine discards the `apis`-branch foundation this RFC builds on — the Ray-based monitoring backend, the dispatcher, the Ray Dashboard observability story (§5) — and substitutes a second, unrelated runtime and its operational burden. For a small team on SARAO HPC already moving toward Ray, taking on Nextflow's or Snakemake's full operational model to then fight it over in-memory handoff is a poor trade.

### (c) Skip transpilation entirely and write pipelines as Python from the start

**What it is.** If the target is an auditable Ray-orchestrated Python package, write that package by hand. Drop the YAML recipe layer and the compiler; maintainers author `tasks.py`/`runner.py`/`cli.py` directly against `hip_cargo.runtime`. This is the simplest possible thing and would produce exactly the artifact §1 wants, with no codegen to build or maintain.

**Why not chosen — though it is partly endorsed.** This RFC's own next-steps (§12) call for *hand-writing* the `stokify` runner before any transpiler exists, precisely because hand-authored Python is the cleanest way to validate the target shape and the in-memory model end-to-end. So the disagreement is narrow. The case for keeping a recipe layer is threefold. First, the recipe is the auditable unit reviewers and operators already read: a restricted YAML recipe with no shell and no DSL is reviewable by inspection (§2.2) in a way a hand-written Ray driver — with its `ray.init`, ObjectRef plumbing, `runtime_env` dicts, and resource decorators — is not, and hand-authored drivers drift from any reviewable contract over time. Second, the recipe → runner mapping enforces the restriction mechanically: a transpiler that only accepts the restricted grammar cannot emit a shell call or a DSL evaluation, whereas a human writing Python directly can reach for `subprocess`, `eval`, or an ad-hoc ObjectRef pattern that breaks the driver-never-materializes invariant, and nothing structural stops them. Third, the codegen reuses machinery the `apis` branch already provides (the shared IR, `generate_parameter_signature`, the lazy-import call pattern), so the marginal cost of the compiler is lower than it appears, and the per-step `runtime_env`/resource wiring it standardises is exactly the boilerplate most likely to be gotten subtly wrong by hand. The transpiler earns its place by making the *restriction* and the *invariants* properties of the toolchain rather than of programmer discipline. We acknowledge the residual uncertainty: if, after the hand-written `stokify` spike, the recipe layer turns out to add little over well-factored Python helpers, "skip the compiler" remains a legitimate fallback — this is a discussion document, and that outcome would not be a failure.

### (d) Use Prefect / Flyte / Airflow as the workflow engine

**What it is.** Adopt a Python-native orchestration framework — Prefect, Flyte, or Airflow — as the execution engine instead of orchestrating Ray tasks directly. Each offers task graphs expressed in Python, retries, scheduling, a UI, and (Flyte especially) per-task containerisation and typed interfaces; Flyte in particular targets exactly the "typed Python tasks in containers" shape this proposal cares about.

**Why not chosen.** The decisive factor is the in-memory dataflow. The design's load-bearing mechanism is the Ray ObjectRef / plasma store: `init.remote() → ref → process.remote(ref) → ref → image.remote(ref)`, with `memory_greedy` keeping an `xr.Dataset` resident in plasma so that no intermediate is serialised to disk and the driver never materialises it. Prefect and Airflow are orchestrators rather than distributed object stores; passing a large `xr.Dataset` between their tasks generally routes through a result store / XCom / serialised return that lands on disk or in a backend, which defeats `memory_greedy` and reintroduces exactly the I/O we are trying to skip. Flyte is the closest fit — typed, containerised tasks are its model — but it likewise passes data between tasks by writing typed offloaded blobs to a blob store between task containers, so the zero-disk intermediate handoff is again not native; and adopting Flyte brings a substantial control-plane (its own backend, registration model, and operational surface) onto SARAO HPC. Against all three, the reuse argument also weighs heavily: the `apis` branch is already Ray-based — the monitoring backend aggregates Ray progress events, the submission path already uses the Ray Jobs SDK, and observability is planned on the Ray Dashboard (§5). Ray was reconsidered and deliberately kept (§1); switching engines would discard that ~70% and trade a single distributed-compute substrate for an orchestrator layered *on top of* a compute substrate. We do not claim Ray is strictly superior as a general orchestrator — Prefect's and Airflow's scheduling, retry, and operational ergonomics are more mature — only that the specific in-memory model this RFC is built around is a Ray-native capability the others do not offer cheaply.

### (e) Extend the monitoring server to launch pipelines from YAML directly, without the transpiler step

**What it is.** The `apis`-branch monitoring server already has a submission endpoint that builds a command and submits it via the Ray Jobs SDK. The minimal-change option is to keep interpreting the recipe at submit time: have the server (or a small interpreter behind it) read the restricted YAML, resolve the DAG, and launch the steps directly — no compiled package, no generated `tasks.py`/`runner.py`. This avoids inventing a codegen path at all and reuses most of the existing server.

**Why not chosen.** This is the status quo the proposal is reacting to, and it is informative about what we are trying to leave behind. Today that endpoint constructs a `stimela run <recipe> <key> <args>` *string* and submits it as a job entrypoint — the "fragile string builder" §9 flags for replacement. A YAML-at-submit-time interpreter, even a restricted one, has two problems the transpiler is designed to fix. First, there is no auditable artifact: the thing that runs is reconstructed in the server at submit time, so the §1/§2.2 guarantees — a concrete Python package you can `ruff`/`bandit`, version, review, and ship independently — never come into existence. A clean `bandit` run is only meaningful as a *negative result on a concrete generated module* (§2.2); there is nothing to scan if the program is assembled transiently inside the server. Second, an in-server interpreter re-creates, in a long-lived network service, the general-framework interpreter §2 argues against — now positioned as a privileged submission daemon on shared HPC, which is a worse place for run-time dynamism than a user's own process. The transpiler instead moves all interpretation *ahead* of submit time: the server's job becomes invoking an already-compiled, already-audited runner (exactly the §9 change that replaces the string builder), which is both simpler for the server and stronger for the audit story. The existing endpoint and Ray Jobs SDK wiring are not wasted — they are reused as the submission substrate — but the recipe is compiled before it reaches them, not interpreted after.

## 11. Open questions

The proposal is deliberately scoped, and the cuts in Section 6 are commitments rather than oversights. But several of them sit on movable lines, and a few design dependencies are genuinely unresolved. This section records the questions we know we are deferring, so that the working group can push back on the framing before any of them is answered by accident in code.

**Conditional-by-specialization: a possible future relaxation of the formula-DSL cut.** Section 6 excludes `=IF`/`=IFSET` (all arities) along with the rest of the formula DSL, and §2.2 explains why: a value computed by a run-time evaluator is opaque to `ruff` and `bandit`, so admitting it would breach the static-analysability boundary the whole proposal rests on. That argument is sound *for the general case*, but it is stronger than it needs to be. A formula is only un-analysable if it must be evaluated at run time. If a conditional can be **evaluated up front** — at transpile time, given the concrete inputs the user is compiling against — then it is not run-time dynamism at all; it is a compile-time constant. Under that observation, `=IF`/`=IFSET` could be re-admitted not by teaching the runner to evaluate them, but by teaching the *transpiler* to: each distinct input signature would resolve the conditionals to concrete bindings and emit a **different specialized recipe per signature**, one transpiled package per distinct input shape. The analogy is numba's `@overload`/dispatch model: a family of statically-typed, separately-compiled specializations behind one logical entry point, rather than a single body that branches at run time. The key property is preserved — every *emitted* variant is still plain, branch-free Python that `ruff` and `bandit` can read on the page — so this would restore conditional expressiveness without reopening the injection or opacity surface §2.2 closes. The open questions are two, and both are real. First, *where does "evaluable up front" end?* A conditional on a literal recipe parameter is clearly evaluable; one on a value only known after `init` reads a measurement set clearly is not; the interesting cases (e.g. a branch on a band count that is itself a typed input) lie in between, and we have no crisp predicate for that boundary yet. Second, *where does specialization explosion begin?* The cross-product of independent conditionals grows combinatorially, and a recipe with a handful of orthogonal `=IF`s could demand an unmanageable number of emitted packages. This relaxation is therefore noted as a plausible direction, explicitly not part of v1, and gated on finding a tractable answer to both boundaries before it is worth building.

**Packaging boundary between `hip-cargo`, `hip_cargo.runtime`, and `hip-cargo[monitoring]`.** Section 9 introduces a `hip_cargo.runtime` subpackage (Ray submit helpers, the ObjectRef-chaining runner template, memory-mode helpers) that transpiled packages depend on, and it must stay installable without the heavy scientific stack — that is the whole point of the lightweight driver. Today the repository has the base package and a `monitoring` optional extra (FastAPI/uvicorn/websockets) but no `runtime` subpackage at all. The open question is exactly where the cut lines fall. Does `hip_cargo.runtime` pull in Ray as a hard dependency of the base install, or as its own extra (`hip-cargo[runtime]`), so that someone who only wants `generate-cabs` is not forced to install Ray? Is `runtime` allowed to depend on anything in `monitoring`, or must the dependency point strictly the other way? A transpiled `stokify` package needs `hip_cargo.runtime` to submit, but should it need `hip-cargo[monitoring]` to be *observed*, or should observation attach out-of-band via the Ray Dashboard with the monitoring server as an optional overlay? These are answerable, but they need answering deliberately rather than emerging from whatever the first spike happens to import.

**Governance and divergence risk across the three layers.** Once `hip_cargo.runtime` is a runtime dependency of every transpiled package, its template code is effectively an API contract shared by an unbounded set of downstream packages compiled at different times against different versions. A transpiled package pins the runner shape it was generated against; the installed `hip_cargo.runtime` may be newer. We have no answer yet for how the runner template, the cab schema, and the monitoring protocol stay in lockstep, nor for what a version-skew policy looks like when a package transpiled last year is run against this year's runtime. The risk is concrete: the three layers can drift independently, and the proposal currently assumes a coherence it does not specify how to enforce. A version-skew policy is therefore needed *before* the first transpiled package ships to external users, not after — at minimum, a semver contract on `hip_cargo.runtime`'s public API surface, so a package can declare the runtime range it was compiled against and fail loudly rather than silently against an incompatible one.

**Nested recipes in the IR.** The current IR (`utils/spec.py`: `ParamSpec`/`CommandSpec`/`ModuleSpec`) models the inside of a *cab* — the typed parameters of one Python callable — and has no representation of a *recipe* at all, let alone a recipe whose step is itself a recipe. The linear `stokify` demonstrator does not need one. But stimela recipes nest routinely, and a transpiler that cannot represent a sub-recipe as a node will not generalize beyond toy pipelines. The open question is whether a nested recipe lowers to a nested Ray task graph (a sub-DAG inlined into the parent), to a separately-transpiled sub-package the parent imports and calls, or to something the IR refuses and reports as unsupported. This interacts directly with the §6 `_use`/`_include` cut: we have excluded YAML-level composition, so nesting, if admitted, must be expressed structurally in the IR rather than as a merge layer — but the IR shape for that is undecided.

**What locality and resource hints belong on cabs versus on steps.** The design declares resources per step on the `@ray.remote` decorator (`num_cpus`/`num_gpus`/`memory`), and carries the container image and `env_vars`/`run_options` in each cab's already-declared `runtime_env`. That split is clean for the things that are unambiguously one or the other, but several hints are genuinely ambiguous. A GPU requirement is arguably a property of the *cab* (the tool needs a GPU wherever it runs) and also of the *step* (this invocation wants two of them). Data-locality hints — "schedule near the shared store", "co-locate with the producer's plasma object" — have no obvious home at all. The open question is which hints are intrinsic to a wrapped tool (and therefore belong in the cab schema, defaulted once by the wrapper maintainer) versus per-invocation tuning (and therefore belong on the step in the recipe, overriding the cab default). Getting this wrong pushes either boilerplate into every recipe or policy into every cab.

**Ray version compatibility and the `image_uri` experimental-status mitigation.** Three things must agree on a Ray version: the cluster the driver connects to, the transpiler that emits the runner, and the runtime each transpiled package was compiled against. We have no stated compatibility policy across those three, and Ray's API surface around `runtime_env` is exactly the part most likely to move between releases. The acute case is the per-task `runtime_env` `image_uri` that the entire per-step-container model depends on: it is marked experimental upstream (§1, §5), which means it can change shape or be withdrawn between Ray versions with no deprecation guarantee. The open question is the mitigation. Options include pinning a known-good Ray version for the whole SARAO deployment and tracking `image_uri` upstream until it stabilizes; abstracting the container-launch behind a `hip_cargo.runtime` shim so a future API change is a one-place edit rather than a regeneration of every package; or falling back to a non-`image_uri` mechanism (e.g. launching workers into pre-imaged Ray nodes) if the experimental API proves too unstable to depend on. None of these is chosen, and the choice materially affects how much the experimental status actually costs us. This dependency should be validated **explicitly and early**, as a named milestone of the §12 spike: does per-task `image_uri` actually work on SARAO's target Ray version with the container runtime in use? The check is cheap and load-bearing — it is far better to learn the answer on a synthetic single-image pipeline than after the per-step-container model has been committed to.

**Shared filesystem versus object store.** `memory_greedy` keeps intermediates plasma-resident and touches no disk between steps, so it is indifferent to where storage lives. `memory_conservative` is not: it returns a small, lazily store-backed `xr.Dataset` (e.g. `xr.open_zarr(...)` without dask) and *defers* its reads to a shared store rather than eliminating them, which means it assumes a store every worker can reach. That sharpens a decision the proposal has so far left open — is the reachable store a shared POSIX mount (e.g. the `/scratch:ro` bind in the §5 sketch) or an object store (S3/GCS/Azure, for which hip-cargo already carries fsspec backends)? The two have different consistency, latency, and credential-forwarding characteristics, and `memory_conservative` correctness depends on which one is assumed. The open question is whether the recipe should be allowed to *state* its store assumption, whether the transpiler should refuse `conservative` mode when no reachable store is configured, and how this interacts with the per-scheme credential forwarding the runtime already does for remote URIs. The honest position is that `conservative` mode trades a memory win for a deployment assumption, and we have not yet committed to which deployment.

**The migration story for existing stimela users.** The proposal is explicitly a *hardening target for mature recipes*, not a replacement for stimela's development role (§2), which makes the on-ramp from an existing recipe a first-class concern rather than an afterthought. A maintainer with a working stimela recipe will, reasonably, want to point the transpiler at it and see what happens. The open question is what "what happens" should be. The desirable shape is a transpile *attempt* that succeeds when the recipe already lies within the restricted subset, and otherwise fails *gracefully and specifically* — naming each unsupported feature it encountered (this step uses `=IF`; this alias is a `*.x` broadcast; this cab is a CASA flavour) and, where possible, pointing at the §6 exclusion and the flattening it would require. The contrast we want to avoid is a generic parse failure that tells the user nothing actionable. This is partly a UX question and partly a question about how much of stimela's grammar the transpiler must *parse* (in order to diagnose) even though it will not *transpile* it — a non-trivial amount of front-end work that buys no run-time capability, only a humane failure.

## 12. Proposed next steps

The next step is a small, concrete spike staged around the `stokify` demonstrator. Its purpose is to validate the *target shape* and the in-memory model before committing to a transpiler, not to build the transpiler. We propose the stages below, in order; the deliverable of the whole spike is a set of hand-written exemplars, a *runnable* synthetic demonstrator streaming live progress through the existing monitoring stack, and a validated IR sketch — explicitly **not** a working transpiler.

**1. Scaffold `stokify` via `hip-cargo init`.** Stand up `stokify` as a strictly-conforming three-step package — `init` (read a measurement set), `process` (coherencies → image-ready Stokes visibilities), `image` (grid and image the Stokes visibilities) — each step a plain Python `core/` function returning an `xr.Dataset`, each wrapped in the standard `cli/` + `cabs/` shape that `hip-cargo init` already produces. The point of scaffolding it through `init` rather than by hand is to prove that the package the design advocates is the package the existing tooling already generates. This stage also fixes the `memory_greedy`/`memory_conservative` contract in concrete code: the mode arrives as a `Literal["greedy","conservative"]`, the static return type is `xr.Dataset` in both modes, and each `core/` function branches internally between a reified plasma-resident dataset (greedy) and a small lazily store-backed one (conservative) — both avoiding any *write* of an intermediate to disk. Getting this contract right in hand-written `core/` functions is a precondition for everything downstream, because the transpiler will never re-implement these bodies; it only imports and calls them.

**2. Hand-write the transpiled output for the linear recipe — before building any transpiler.** Write `tasks.py`, `runner.py`, and `cli.py` for the linear `stokify` recipe by hand, as exemplars of exactly what the transpiler must eventually emit. `tasks.py` carries the three `@ray.remote` task wrappers, each with its per-step container `runtime_env` (the cab's declared image plus `env_vars`/`run_options`) and per-step resource request, with the heavy import performed *inside* the task body so it lives in the container image and not on the driver. `runner.py` chains the steps purely by ObjectRef — `init.remote()` → ref → `process.remote(ref)` → ref → `image.remote(ref)` — holding only opaque refs and never calling `ray.get` on an intermediate, so the driver never materializes an `xr.Dataset` and the lightweight install on the driver never needs the heavy stack. `cli.py` is the thin lightweight driver that parses arguments, threads the memory mode through, and submits the graph. Writing these by hand first is the cheapest way to discover whether the target shape is actually coherent end-to-end — whether the ObjectRef chaining, the per-step `runtime_env`, and the driver-never-materializes principle compose without surprises — *before* we encode any of it as codegen. If the hand-written version is awkward, the transpiler would only have automated the awkwardness.

**2.5. Exercise the monitoring server with the hand-written runner — make the demonstrator *runnable*.** This is what turns a set of plausible modules into something a reviewer can see working, and it is the most persuasive single artifact the spike can produce. The `stokify` `core/` functions operate on **synthetic data** (an `xr.Dataset` of realistic shape, e.g. `(band, stokes, x, y)`, with simulated per-iteration compute), so the pipeline runs anywhere with no measurement-set or radio-astronomy dependencies, and each step emits real `track_progress()` events with realistic metrics (a falling residual, a rising convergence). The runner registers a `RayProgressBackend` against a `get_or_create_aggregator()` actor and drives the linear chain on a **local Ray cluster**. With `hip-cargo monitor --port 8321` running in one terminal and the pipeline in another, the spike verifies that real events flow end-to-end through the existing stack — `GET /api/progress/{job_id}` (latest), `.../events`, `.../metrics/{name}`, `.../dag`, and the `WS /ws/progress/{job_id}` stream — driven by a small integration/demo script that starts Ray, wires the backend, runs the pipeline, queries the API, and prints a summary. Two honesty notes bound the claim. First, this exercises the monitoring substrate and the ObjectRef/`track_progress` plumbing, **not** the per-step container path: the local run does not launch `image_uri` containers (that is the separate experimental-validation milestone, above and in §11), so `tasks.py` carries the `runtime_env` shape the transpiler would emit while the local runner executes the steps in-process. Second, on a single node the `greedy`/`conservative` distinction is largely **cosmetic** — plasma versus a local zarr on the same disk — so this stage demonstrates the *contract and the event flow*, not the disk-bypass performance characteristic, which only a real cluster shows. The deliverable is a reviewer-runnable demo: `pip install` both packages, run `hip-cargo monitor` and `stokify`, and watch live progress at `localhost:8321`.

**3. Validate the codegen bar against the hand-written exemplars.** Treat the hand-written `tasks.py`/`runner.py`/`cli.py` as the artifact a transpiler would have produced, and check them against the full quality bar the eventual generated output must clear: the package installs lightweight (driver and `hip_cargo.runtime` only, heavy deps confined to the per-step container image); the CLI builds and its `--help` resolves; the generated Python is `ruff`-clean *and* `bandit`-clean — recalling from §2.2 that a clean `bandit` run is a meaningful negative result *given the restricted input grammar*, not a proof of behavioural safety and not whole-program data-flow tracing; and the DAG and its bindings resolve, verified with a structural / dry-run check (DAG topology, ObjectRef wiring, named-argument bindings) that does not execute the scientific code. **Live execution on a real measurement set is a separate, opt-in milestone**, deliberately outside this spike: it depends on cluster access, a built container image, and the experimental `image_uri` path working in practice, and gating the structural validation on it would conflate "the shape is right" with "the cluster is available." This stage is what turns "we wrote some plausible Python" into "we know the generated shape clears the bar we will hold the transpiler to."

**4. Generalize the IR against further recipe shapes.** Only once the linear `stokify` shape is proven end-to-end do we widen the IR. The current IR (`ParamSpec`/`CommandSpec`/`ModuleSpec` in `utils/spec.py`) models the inside of a cab; a recipe-level IR — steps, bindings, and the dataflow edges between them — is new work, and the right time to design it is after the linear case has shown what the runner actually needs from it. We then sketch (not implement) how that IR extends to `for_loop`, `scatter`, and nested recipes (the last connecting back to the nested-recipe open question in §11), so that the v1 IR is shaped with an eye to the shapes it will eventually have to carry rather than being retrofitted later. The output of this stage is a *validated IR sketch* — concrete enough that an engineer can sanity-check it against both the linear demonstrator and the next shapes — not a parser or a code generator.

To restate the boundary plainly: the deliverable of this spike is the hand-written `stokify` exemplars, a runnable synthetic demonstrator streaming live progress through the monitoring stack, and the validated IR sketch. A working transpiler is the *next* proposal, and is justified only if these exemplars demonstrate that the target shape is coherent, auditable, and worth automating.
