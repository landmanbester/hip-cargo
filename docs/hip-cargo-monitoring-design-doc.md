**Status:** Backend complete, frontend pending redesign

## 1. Goals

### 1.1 Primary Goal

Equip hip-cargo with an automatic API layer so that any project using the
hip-cargo template can expose a web-based monitoring dashboard with minimal
additional effort. Users should be able to:

- View the progress of long-running scientific computing pipelines from any
  device (desktop or phone)
- Inspect intermediate outputs and convergence metrics in real time
- Kill a running pipeline step and relaunch it with modified parameters
- Launch new pipeline runs from a graphical interface

### 1.2 Broader Vision

The monitoring system is a first step toward a larger goal: an intelligent
workflow orchestration tool for radio astronomy pipelines. The full vision
includes:

- **Visual DAG representation** of stimela recipes (n8n-style flow diagrams)
  showing how pipeline steps connect their inputs and outputs
- **AI agent insertion points** between pipeline steps for automated quality
  assurance and parameter tuning
- **A recipe transpiler** that converts stimela recipes into installable Python
  packages, supporting only the safe subset of stimela features used by
  hip-cargo-style packages
- **Automatic API generation** from hip-cargo decorator metadata, so any
  decorated function is automatically accessible via REST and WebSocket

### 1.3 Design Principles

- **Leverage Ray's existing infrastructure**: the monitoring server is a thin
  proxy over Ray's Jobs API and Dashboard, not a replacement for them
- **Zero overhead when monitoring is off**: the progress protocol uses a
  NullBackend by default, adding no cost to uninstrumented code
- **Cab YAML as the source of truth**: parameter schemas come from cab
  definitions generated by hip-cargo decorators, not from runtime introspection
- **Functional style**: protocol and utilities are functions and dataclasses,
  classes used only where they maintain necessary state (e.g. ProgressTracker,
  ProgressAggregator)
- **SSH-first authentication**: primary access is via SSH tunnel to the cluster
  head node; bearer token auth is a secondary option for cloud deployments

### 1.4 Target Use Case

The primary use case is pfb-imaging: a radio interferometric imaging package
that processes data from the MeerKAT radio telescope. Typical workloads involve
image cubes of shape `(n_band, n_stokes, n_x, n_y)` where `n_band=8`,
`n_stokes=1,2,4`, and both `n_x` and `n_y` range from 6000–10000 pixels.
Pipelines are defined as stimela recipes (YAML files) that chain together
steps such as `init → grid → sara → restore → degrid`, where each step may
internally use Ray for parallelism across workers.

### 2.2 Implemented Components (by phase)

#### Phase 1: Progress Event Protocol

**Files:**
- `src/hip_cargo/utils/progress.py`
- `src/hip_cargo/utils/progress_context.py`
- `tests/test_progress.py`

**What it provides:**

The core abstraction for progress reporting. Workers emit structured
`ProgressEvent` dataclasses through a pluggable backend protocol.

`EventType` enum with 11 event types:
- Worker-level: `started`, `progress`, `log`, `artifact`, `metric`,
  `completed`, `failed`
- Pipeline-level: `pipeline_started`, `step_started`, `step_completed`,
  `step_failed`

`ProgressBackend` protocol (runtime-checkable) with `emit()` and `close()`
methods. `NullBackend` is the default — zero overhead when monitoring is off.

Module-level API: `set_backend()`, `get_backend()`, `emit()`.

`track_progress()` context manager provides ergonomic progress tracking:

```python
with track_progress("sara", total_steps=n_major, job_id=run_id) as tracker:
    for i in range(n_major):
        tracker.step(message=f"Major cycle {i+1}")
        tracker.metric("peak_residual", float(residual.max()))
        tracker.artifact("/tmp/residual.png", "image")
```

Automatically emits STARTED on entry, COMPLETED on success, FAILED on
exception. The `pipeline_run_id` parameter groups steps belonging to the
same pipeline run.

**Design decisions:**
- Pure Python, zero dependencies beyond stdlib
- Flat event model (major cycles only, not inner solver iterations) —
  sufficient for dashboard monitoring
- `extra: dict` field on ProgressEvent provides escape hatch for future
  extensions (DAG structures, object refs, agent feedback)
- Thread safety via per-process globals (Ray gives each worker its own
  Python interpreter)

#### Phase 2: Recipe Parser

**Files:**
- `src/hip_cargo/monitoring/recipe_parser.py`
- `tests/test_recipe_parser.py`
- `tests/fixtures/sara.yml`

**What it provides:**

Parses stimela recipe YAML files into structured `RecipeDAG` objects
containing:
- `RecipeInput` — recipe-level parameters (name, dtype, required, default,
  info, aliases)
- `RecipeStep` — ordered steps with cab reference, parameter bindings
- `StepParam` — individual parameter bindings classified as literal vs
  binding (`=recipe.xxx`, `=IFSET(...)`, `=IF(...)`, expressions)
- `edges` — execution order edges (currently linear, extensible to
  support stimela's scatter construct in future)

The parser extracts `recipe.xxx` references from binding expressions via
regex, enabling the frontend to show parameter flow between recipe inputs
and step params. It does NOT evaluate stimela expressions — only classifies
and extracts references.

Key function: `parse_recipe(path, resolve_cabs=True) -> RecipeDAG`

When `resolve_cabs=True`, the parser resolves `_include` entries to actual
cab YAML files and attaches full parameter schemas to each step (see
Phase 3b Fixes below).

#### Phase 3a: Configuration + Ray Backend

**Files:**
- `src/hip_cargo/monitoring/config.py`
- `src/hip_cargo/monitoring/ray_backend.py`
- `tests/test_config.py`
- `tests/test_ray_backend.py`

**What it provides:**

`MonitorSettings` (pydantic-settings): reads from environment variables
with `HIPCARGO_` prefix and/or `.env` files. Settings include: auth_token,
host, port, ray_address, ray_dashboard_url, aggregator_name,
max_events_per_job, websocket_poll_interval, recipes_dir, cli_module.

`ProgressAggregator` (Ray actor): collects progress events from all workers.
Methods: `push_event()`, `get_latest()`, `get_events()` (with cursor-based
incremental fetch), `get_all_jobs()`, `get_metrics_history()`,
`get_pipeline_dag()`. Uses a ring buffer (configurable max, trims to half
when exceeded) to bound memory.

`RayProgressBackend`: implements `ProgressBackend` protocol, pushes events
to the aggregator via fire-and-forget remote calls (non-blocking to workers).

`get_or_create_aggregator()`: helper that gets an existing named actor or
creates a new detached one.

**Known issue resolved during implementation:** Ray 2.40+ auto-detects
the project directory and creates a separate venv for workers, which
doesn't include ray itself. Fix: pass `runtime_env={"working_dir": None}`
to `ray.init()` in test environments. This affects any downstream project
running Ray actors from within project directories.

#### Phase 3b: FastAPI Server + CLI

**Files:**
- `src/hip_cargo/monitoring/server.py`
- `src/hip_cargo/monitoring/dispatcher.py`
- `src/hip_cargo/monitoring/cab_resolver.py`
- `src/hip_cargo/monitoring/recipe_discovery.py`
- `src/hip_cargo/cli/monitor.py`
- `tests/test_server.py`
- `tests/test_dispatcher.py`
- `tests/test_cab_resolver.py`
- `tests/mocks.py`

**What it provides:**

FastAPI application (`create_app(settings)`) with these endpoint groups:

**Job management (via Ray Jobs Python SDK):**
- `GET /api/jobs` — list all jobs, enriched with progress data
- `GET /api/jobs/{job_id}` — get job details + progress
- `GET /api/jobs/{job_id}/logs` — get job logs
- `POST /api/jobs/{job_id}/stop` — stop a running job
- `POST /api/pipelines/submit` — submit a new pipeline run from a recipe

All Ray Jobs SDK calls go through `_run_sync()` (thread pool executor) to
avoid blocking the async event loop. `JobSubmissionClient` is synchronous
internally.

**Progress data (from ProgressAggregator):**
- `GET /api/progress/{job_id}` — latest progress event
- `GET /api/progress/{job_id}/events?since=0` — incremental event fetch
- `GET /api/progress/{job_id}/metrics/{metric_name}` — metric time series
- `GET /api/progress/{job_id}/dag` — pipeline DAG structure
- `WS /ws/progress/{job_id}` — real-time event streaming

**Recipes and commands:**
- `GET /api/recipes` — list available recipes
- `GET /api/recipes/{recipe_name}` — parsed DAG with cab schemas
- `GET /api/commands` — list available cabs with parameter schemas

**Infrastructure:**
- Token-based auth middleware (optional, for cloud deployments)
- WebSocket auth via query parameter
- Static file serving for frontend assets
- Placeholder HTML at `/` with link to `/docs` (Swagger UI)

**EventDispatcher:** single background asyncio.Task polls the aggregator
for all subscribed jobs, fans out events to per-connection `asyncio.Queue`
instances. One poll loop serves N WebSocket clients. Includes heartbeat
messages (30s timeout) to keep connections alive through proxies, and
guaranteed cleanup on disconnect via `finally` block.

**Cab resolver:** resolves `_include` entries from recipe YAML
(format: `(python.module)filename.yml`) to actual cab files on disk via
`importlib.import_module()`. Parses cab YAML into `CabSchema` dataclasses
with full input/output parameter schemas (`CabParam`). This replaces the
original `inspect.signature`-based discovery module.

**CLI command:** `hip-cargo monitor` launches the dashboard with configurable
port, host, ray_address, ray_dashboard_url, and auth_token. All heavy imports
(FastAPI, uvicorn, Ray) are lazy-loaded inside the function body.

**Design notes from implementation:**
- Auth middleware uses `JSONResponse(status_code=401)` directly rather than
  raising HTTPException (which BaseHTTPMiddleware doesn't handle correctly)
- TestClient runs the app's lifespan, so tests override
  `app.router.lifespan_context` with a no-op that injects mock state
- `FakeAggregator` in tests replicates Ray's `.method.remote()` calling
  convention using `_RemoteMethod`/`_FakeRef` wrappers
- WebSocket backpressure: if a client is slow and its queue fills up,
  `put_nowait` fails and the dispatcher removes the subscriber. Default
  `asyncio.Queue` is unbounded; setting a maxsize (e.g. 1000) would bound
  per-connection memory
- Each job_id has a single cursor shared across subscribers — new
  subscribers only see events from join-time forward, not historical events

## 3. What Still Needs to Be Done

### 3.1 Frontend (Redesigned)

The initial plan was to use Google Stitch to design a React/Tailwind frontend
served as static files by the FastAPI server. The Stitch iteration did not
produce satisfactory results.

The new direction is to build the frontend as part of a **recipe transpiler**
that converts stimela recipes into installable Python packages. This changes
the frontend from a standalone monitoring app into an integrated component
of the transpiled package.

**Original frontend design (for reference):**
- Dark theme, n8n-inspired
- Two-level navigation: outer DAG view, inner step detail
- Pipeline DAG via React Flow with custom step nodes
- Step detail: progress bar, Recharts metric charts, image preview, log tail
- Parameter editing panel for kill-and-relaunch
- Responsive: desktop (sidebar + slide-in panel) / mobile (bottom tabs)

**Key screens prioritised:**
1. Pipeline DAG flow diagram (primary screen)
2. Step-level progress and metrics
3. Cluster status (link to Ray Dashboard)

The backend API is fully built and tested. The OpenAPI schema at `/docs`
describes every endpoint. The frontend can be implemented against this
stable API.

### 3.2 Recipe Transpiler (New Feature)

A new tool that converts stimela recipe YAML files into installable Python
packages. This is a significant new direction that builds on top of the
existing monitoring infrastructure.

**Scope:** The transpiler supports only the safe subset of stimela features
used by hip-cargo-style packages:

- `_include` references to hip-cargo cabs (resolved via `cab_resolver.py`)
- Sequential step execution (linear DAG, plus future scatter support)
- Recipe-level inputs with type declarations
- Step parameter bindings (`=recipe.xxx`, `=IFSET(...)`, `=IF(...)`)
- Aliases for broadcasting values to step params

The recipe parser (`recipe_parser.py`) and cab resolver (`cab_resolver.py`)
already provide the foundation for this — they can parse a recipe, resolve
its cab dependencies, and extract full parameter schemas.

**What the transpiler would produce:**
- A Python package with a CLI entry point for each recipe
- Ray-based pipeline runner that executes steps in DAG order
- Progress instrumentation built in (using `track_progress()`)
- The monitoring server and frontend as an optional dependency
- Installable via pip/uv

### 3.3 `ray.util.metrics` Integration

The original design called for workers to dual-write: pushing events to the
custom ProgressAggregator (for structured streaming) AND updating
`ray.util.metrics` Gauges/Counters (for Prometheus/Grafana via Ray Dashboard).
This was not implemented yet.

Relevant metrics to export:
- `pfb_progress_fraction` (Gauge) — progress 0–1 per worker/job
- `pfb_peak_residual` (Gauge) — peak residual per worker/job
- `pfb_major_cycles_total` (Counter) — cycles completed per worker/job

This would be added to `ProgressTracker.step()` and `ProgressTracker.metric()`
methods, writing to both the custom backend and the Ray metrics registry.

### 3.4 Artifact Serving

The design for image artifact serving via Ray object store was sketched but
not implemented. The plan:

- Workers generate 256px PNG thumbnails from intermediate images
  (handling n_band/n_stokes dimensions)
- Push thumbnails into Ray object store via `ray.put()`
- Report object ref hex string in the `extra` field of ARTIFACT events
- FastAPI endpoint `GET /api/artifacts/{ref}` retrieves and serves the PNG
- Full-resolution artifacts (FITS, zarr) served from shared filesystem

### 3.5 Pipeline Runner

No pipeline runner exists yet. Currently, pipelines are submitted as
`stimela run` commands via the Ray Jobs API. The transpiler feature would
replace this with a native Python pipeline runner that:

- Executes steps in DAG order
- Passes outputs from one step as inputs to the next
- Emits pipeline-level progress events (PIPELINE_STARTED, STEP_STARTED, etc.)
- Supports killing and relaunching individual steps (keeping upstream outputs)
- Could eventually support AI agent insertion points between steps

### 3.6 Template Updates

`hip-cargo init` should generate:
- A `monitoring/` directory with a DESIGN.md and placeholder static files
- A `.env.example` file (committed to git) with monitoring settings
- `.env` added to `.gitignore`
- Documentation on how to enable and use the monitoring dashboard

### 3.7 Per-Task Diagnostics (Implemented)

Implemented (`utils/diagnostics.py`, `monitoring/diagnostics_report.py`);
current reference: `docs/wiki/diagnostics.md`; rationale: transpile RFC §5.10. The goal
is the diagnostic breakdown an optimising agent needs: what each task
actually consumed versus what it requested. Stimela profiles too coarsely
for this, and Ray's Dashboard/state API do not attribute in-process
consumption to hip-cargo's job/step vocabulary.

- **Capture:** stdlib-only `ResourceSnapshot` (`time.perf_counter` +
  `resource.getrusage(RUSAGE_SELF)`) at entry/exit of `track_progress(...)`;
  the delta (wall, user/system CPU, peak RSS, block I/O) is emitted as one
  new `DIAGNOSTIC` event with the payload in `extra["diagnostics"]`. No
  `ProgressEvent` schema change; `NullBackend` keeps it zero-overhead.
  Transpiled `tasks.py` wrappers additionally record `import_s` (container
  cold-start).
- **Optional tiers:** `psutil` (sampled true in-task peak RSS, I/O bytes)
  and `pynvml` (GPU memory/utilisation) when importable; never required.
- **Serving:** `ProgressAggregator.get_diagnostics(job_id)` joins the
  in-worker deltas with the step timeline (`queue_lag_s` from
  `STEP_STARTED` → worker `STARTED`) and the declared per-step resource
  requests; served at `GET /api/progress/{id}/diagnostics` with stable,
  unit-suffixed field names and derived utilisation ratios.
- **Caveats:** `ru_maxrss` is a process high-water mark under Ray worker
  reuse (both `rss_entry_mb` and `peak_rss_mb` are reported so consumers can
  detect a stale peak); child-process consumption is not attributed; this is
  step-level diagnostics, not line-level profiling.

This complements §3.3 rather than replacing it: `ray.util.metrics` export
targets the Prometheus/Grafana time-series view, while diagnostics serve the
per-task requested-vs-used join as queryable JSON.

## 6. Known Issues and Technical Notes

1. **Pipeline submission param quoting**: The `POST /api/pipelines/submit`
   endpoint builds a `stimela run` command string. Complex values (nested
   lists, paths with special characters) may not be quoted correctly. The
   transpiler feature should replace this with direct Python invocation.

2. **WebSocket cursor sharing**: New WebSocket subscribers to a job that
   already has active subscribers only see events from join-time forward.
   Historical events must be fetched via `GET /api/progress/{id}/events`.

3. **Unbounded WebSocket queues**: The `asyncio.Queue` per subscriber has
   no maxsize by default. A slow client accumulates events in memory.
   Consider setting `maxsize=1000` in production.

4. **Ray worker venv isolation**: Ray 2.40+ creates separate venvs for
   workers when it detects a project directory. Pass
   `runtime_env={"working_dir": None}` to `ray.init()` if workers need
   the project's packages.

5. **Monorepo cab discovery**: `discover_project_cabs()` infers the package
   name from the nearest `pyproject.toml` and imports `{package}.cabs`.
   In a monorepo this picks up whichever project is closest to cwd.

6. **Linear DAG only**: The recipe parser currently builds linear edges
   (each step connects to the next). Stimela's `scatter` construct is not
   yet supported but the edge model (`list[tuple[str, str]]`) can represent
   arbitrary DAGs.
