# Container execution and image lifecycle

Source: `src/hip_cargo/_container_image.py`, `utils/config.py` (readers),
`utils/runner.py` (fallback execution).

## `_container_image.py` — single source of truth

Each hip-cargo-style package declares its container image in a
`_container_image.py` module: `CONTAINER_IMAGE` (URL:tag), optional `GPU`
(`True` / `False` / `"auto"` / a device spec like `"device=0,1"`), and
optional `RUN_ARGS_DOCKER` / `RUN_ARGS_PODMAN` / `RUN_ARGS_APPTAINER` /
`RUN_ARGS_SINGULARITY` (lists, default `[]`). Readers in `utils/config.py`
(`get_container_image`, `get_container_gpu`, `get_container_run_args`) load it
via `importlib` — no CWD dependency, no `uv sync` needed after edits. None of
this appears in cab YAML; the round-trip is untouched.

**Tag lifecycle.** Agents never change the tag; the mechanisms below and the
maintainer do.

1. **Merge to main**: the `update-cabs` workflow resets the tag to `latest`
   via regex, regenerates cabs, commits with `[skip checks]` (the tag only
   stops `update-cabs` re-triggering on its own push; `ci.yml` runs on pull
   requests only, so no CI run sees the commit, and the App bypasses the
   ruleset).
   `publish-container.yml` builds `:latest` on every push to main. The bot
   commit is pushed with the GitHub App token, so it triggers a second build;
   the workflow's `concurrency` group (keyed on `github.ref`) cancels the
   in-flight merge build so `:latest` comes from the newest commit.
2. **Releases**: `tbump` writes the semantic version via before-commit hooks
   in `tbump.toml`; the `v*` tag builds that image. Changelog is
   auto-generated by git-cliff from conventional-commit prefixes (`cliff.toml`).
   The release commit is pushed straight to the default branch, so no CI run
   sees it; `publish.yml` therefore runs the test suite before uploading.
   `publish.yml` and `publish-container.yml` both fire on the tag
   independently, so for the few minutes before the `:X.Y.Z` manifest exists,
   a lightweight install of the new release cannot pull its fallback image.
3. **Feature branches (maintainer only, optional)**: pull requests build no
   image. To test a branch image the maintainer sets the tag by hand to the
   branch name with `/` → `-` (`feat/x` → `:feat-x`) and runs
   `gh workflow run publish-container.yml --ref feat/x`; the workflow's
   `type=ref,event=branch` tag produces the same sanitised name. A branch tag
   merged into main would conflict with the `update-cabs` reset.

Images are multi-arch (amd64 + arm64). Each architecture builds on its own
native runner (`ubuntu-latest`, `ubuntu-24.04-arm`) and is pushed by digest; a
`merge` job applies the tags to one manifest and fails if any built
architecture is missing from it. Native runners rather than QEMU because
emulated arm64 builds are roughly 10x slower, which matters as soon as a
dependency compiles from source. Dropping the arm64 matrix entry gives an
amd64-only image with no other change.

A `meta` job runs `docker/metadata-action` once and feeds both: the OCI labels
(`org.opencontainers.image.source`, `revision`, `version`, ...) must be passed
to each per-arch build because they live in the image config, which
`imagetools create` cannot change; the merge job adds the same metadata as
index-level annotations. (The #121 split first dropped the labels; fixed
before 0.5.0.)

The `Dockerfile` (hip-cargo's and the template's) installs from `uv.lock`:
`uv export --locked --no-dev --extra <full|all> --no-emit-project` piped into
`uv pip install -r`, then the package with `--no-deps`. Each architecture then
gets the same, CI-tested versions instead of resolving independently, and
`--locked` fails the build if `uv.lock` is stale (tbump re-locks on release).
Any `git+` requirement in the export needs `git` in the image (the slim base
has none). That includes a git pin in a dev or test group for a package the
extra also lists, since uv keeps one source per package (meerkat-beams'
`katbeam`), and a hip-cargo pinned through `[tool.uv.sources]`. A GitHub archive
URL (`.../archive/<sha>.tar.gz`) needs no git.

uv enters the image from a named stage (`FROM ghcr.io/astral-sh/uv:<x.y.z> AS
uv`, then `COPY --from=uv`), not `COPY --from=<image>`: Dependabot's Docker
parser reads only `FROM` lines. The `docker` entry in `dependabot.yml` bumps it
monthly. It must not lag the uv that writes `uv.lock`, because the build's
`--locked` re-checks the lock with the image's uv. The same entry ignores minor
and major updates to `python`: the image's Python minor is chosen by hand, and
the `-slim` tag already floats patch releases. `uv_build` in `[build-system]`
is capped at the next uv minor (hip-cargo's and the template's move together),
so bump the cap when Dependabot moves uv past it; a newer uv still builds,
with a warning, by fetching an in-range `uv_build`.

The `hip-cargo init` templates (`templates/workflows/publish-container.yml`,
`templates/claude/rules/architecture.md`, `templates/CLAUDE.md`,
`templates/onboard_core.py`) carry the same lifecycle.

Gotcha: the `generate-cabs` pre-commit hook regenerates cab YAML with the
locked hip-cargo (`uv run --no-sync`, as do tbump and `update-cabs`, so a
global install of another version cannot rewrite them) and can flip a hand-set
branch tag back to `:latest`.
If that happens, restore `src/hip_cargo/cabs/` and commit with
`SKIP=generate-cabs` for non-code commits.

## Container fallback

Generated CLI wrappers bind every parameter into one `params` dict, then
guard only the lazy core import and `preflight_remote_must_exist` with
`try/except ImportError`. The core call, `<name>_core(**params)`, runs in the
`else:` branch: an `ImportError` raised *during* a run (an optional import
inside `core/`, a worker process, a C extension loading a library) propagates
with its traceback instead of silently re-running the command in a container,
where in-place side effects would happen twice (#120). The guard itself
re-raises an `ImportError` whose `name` lies in the command's own package (a
renamed symbol, a deleted module): that is a bug, not a missing install. A
missing dependency names the dependency and fsspec's missing-backend error has
no `name`, so both still fall back; the wrapper prints the caught exception
to stderr first, so a dependency that is installed but unusable (numba
refusing an unsupported NumPy raises a nameless `ImportError`) shows up. A dependency imported lazily inside `core/`
still crashes mid-run rather than falling back; deciding from the `full`
extra's metadata instead is tracked in #132. On fallback
`run_in_container()` reconstructs `sys.argv` from the same `params` and re-runs
the command in the package's container. Because `params` is bound first, the
later `image = get_container_image(...)` cannot shadow a parameter called
`image` (it did, for hip-cargo's own `generate-cabs`, before #120).

Consequences for package authors: heavy imports belong at module scope in
`core/<name>.py`, since only a failing import of `core/` signals a missing
`[full]` install; and core parameter names must match the CLI's, since the
core function is called with `**params`. Backend
priority: `apptainer` → `singularity` → `docker` → `podman`. Volume mounts
resolve automatically from Path-like type hints (ro) and `@stimela_output`
decorators (rw); an input with `StimelaMeta(writable=True)` (cab
`writable: true`, e.g. an MS updated in place) is also mounted rw. Cabs with an `image` field get generated `--backend`
(`auto|native|apptainer|singularity|docker|podman`) and
`--always-pull-images` params, both `{"stimela": {"skip": True}}` so they
never reach cab YAML.

Gotcha: for a cab with an `image`, `generate_function` also puts
`get_container_image` in the top-level `from hip_cargo import ...` line, even
though the body imports it lazily and `ruff check --fix` deletes it. It is
load-bearing: ruff wraps the import before dropping the name, so the name's
length decides whether the final import is exploded. Removing it (as #121 did)
changed the regenerated layout of six downstream CLIs; it was restored and is
pinned by `test_roundtrip_preserves_import_wrapping` (fixture `wrap_demo.py`,
generated by hip-cargo 0.4.0).

## GPU passthrough

`run_in_container` reads `GPU` via
`get_container_gpu(func.__module__.split(".")[0])`, resolves through
`_resolve_gpu_request` (env `HIP_CARGO_GPUS` overrides the constant; `"auto"`
adds flags only when `_gpu_available()` and, for docker/podman,
`_toolkit_available()`), then maps per runtime via `_gpu_args`:

| Runtime | Mechanism |
|---------|-----------|
| docker | `--gpus` (bare index lists normalised to `device=` form) |
| podman | CDI `--device nvidia.com/gpu=...` (host needs `nvidia-ctk cdi generate`) |
| apptainer/singularity | `--nv`; device specs become `CUDA_VISIBLE_DEVICES` |

Host `CUDA_VISIBLE_DEVICES` is forwarded. Explicit device specs target
docker and apptainer/singularity; on podman prefer `True`/`"auto"`/`"all"`
(CDI uses a different device grammar).

## Per-backend run-args

`RUN_ARGS_<BACKEND>` lists are inserted verbatim right after the `run`/`exec`
subcommand for the active runtime. Env `HIP_CARGO_RUN_ARGS` (shlex-split)
appends to whichever backend runs.
